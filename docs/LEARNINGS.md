## Parsing

### Lexers take the first rule that matches, not the longest

Jison, Chevrotain and Langium lexers try their rules in the written order and take the first that matches. Langium puts the keywords first, then the terminals in declaration order, with `LONGER_ALT` only on keywords; Jison gives a keyword literal that ends in a word character an implicit `\b`, and a zero-length match is a token. Most grammar quirks of the types follow from this: keywords that also match as prefixes of names, titles that are read only after another token on the same line, and Jison rules with a leading `.*`, such as `.*direction\s+WORD[^\n]*`, which take the rest of the line (a relation or a label that contains `direction LR` is swallowed). At the end of the input, a Jison lexer in a value state matches the empty string once and then answers its raw end symbol, not `EOF`, which the grammar rejects: a trailing `accTitle:` is a parse error. The scanners keep each rule table in its written order for this reason ([0007](./decisions/0007-hand-written-parsers.md)). **Where:** `crates/ferrigura-syntax/src/scan.rs` and each type's `scanner.rs`.

### Comments and directives end where JavaScript's line terminators end

`cleanupComments` removes `%%` lines with a regular expression in multiline mode, and JavaScript's `^` also matches after U+2028 and U+2029, so a comment can start after a line separator. The directive pattern stops at U+2028, U+2029 and a bare CR. The preprocessor looks after every line terminator JavaScript knows. **Where:** `crates/ferrigura-syntax/src/preprocess.rs` (`loose_directive_len`).

### Detectors are stricter than lexers

The detectors are regular expressions on the start of the text, case-sensitive (`^\s*erDiagram`), and skip only directives and `%%` lines, while several lexers are case-insensitive: `erdiagram` never reaches the ER parser. A type with several keywords (`stateDiagram` and `stateDiagram-v2`) shares one model and renderer, and the SVG's `aria-roledescription` is the detector's id, not the keyword. The headers of the types that ferrigura does not draw are detected with the reference's rules too, so that such a text gets an error that names its type. **Where:** `crates/ferrigura-syntax/src/lib.rs` (`skip_hidden_prefix`, the detectors), `unsupported.rs`, `crates/ferrigura/src/lib.rs`.

## Text measurement and fonts

ferrigura measures text in Rust using host-registered designs and fallback chains, or the retained bundled defaults when no fonts are supplied ([font inputs](./fonts.md)). The measurements below concern the named fixture files, not every font or writing system. The geometry harness registers those files explicitly in Rust and loads the same files as browser fonts; the compatibility snapshots still check the no-input defaults. `crates/ferrigura-text/tests/fixtures/chromium.json` records the text probes and is regenerated by `pnpm -C tools/port port:text-fixture`.

### Widths agree within Chromium's layout unit

Shaping with `harfrust` and summing the advances of a run, kerning and ligatures included, gives the width Chromium reports to within 0.0155 px, which is its layout unit of 1/64 px: Chromium's own canvas and SVG measurements differ from each other by the same amount. Blink keeps positions in units of 1/64 px and converts the advance of each run with a round up, so the next run starts on the grid, and a line's width, the `getComputedTextLength` that Mermaid's wrapping compares, is the sum of the snapped runs. Shaping is one run per word, as Mermaid's per-word `tspan`s are, so no kerning is applied across a space.

This matters because every layout is built on label sizes: a width that is off by a unit moves a wrap or a node. **Where:** `ferrigura-text`, `measure.rs` (`layout_width`, `measure`), `tests/widths.rs`.

### The text box rounds ascent and descent on their own

The Lexica and Atkinson Mono fixture boxes behave like separate half-down rounding after the size is floored to 1/100 px: nominal 28.5 becomes 28. With unrounded metrics those boxes are off by up to 0.36 px; ordinary half-up rounding of the nominal table values misses the ties at 10, 30 and 50 px, half-to-even misses 10 and 50 px, and rounding the sum misses others. These observations do not establish a universal tie rule. The checked Chromium/macOS results are reproduced by normalizing TrueType metrics at 16.16 precision, scaling through the two floating-point stages and rounding each metric; decimal ratios can land below a nominal tie, while an exactly representable ratio such as Inter’s 1984/2048 rounds up at 16 px. The CFF fixture needs a separate precision path. `text_box` follows the checked format-specific behavior; the compatibility helper `text_box_from` retains explicit half-down rounding of already-scaled metrics. **Where:** `metrics.rs` (`text_box`, `text_box_from`, `laid_out_size`), `tests/metrics.rs`, `tests/registry.rs`, `tools/port/text/registered-fonts.ts`.

### `getBBox` of text is wider than its advance

Across, the box of a `<text>` or `<tspan>` is the union of each run's snapped advance and the outline of every glyph in it, so a glyph whose ink reaches past its advance widens the box: the `j` of Lexica Ultralegible starts 0.812 px left of its origin at 14 px, and its italic `f` ends past its advance (the width of "jun" is 20, not 19, at 14 px). Down, the box is the metrics box and the ink never changes it. Wherever the reference reads `getBBox` or `getBoundingClientRect` of SVG text, ferrigura uses `measure_box`; wrapping, layout widths and anchor shifts keep the advance. **Where:** `ferrigura-text`, `bbox.rs`, `tests/extents.rs`; the rule for the custom renderers is `ferrigura-render`, `common/text.rs`.

### Mermaid's wrapping is not CSS wrapping

Mermaid wraps SVG labels with `splitLineToFitWidth` and `splitWordToFitWidth`: it splits a line into words (the segments between Unicode word boundaries, with the spaces as segments of their own), packs words greedily, measures each candidate line as one `tspan` per word with a leading space, and splits a word that does not fit on an empty line into graphemes, at least one per line. The port of exactly that gives the same lines as the JavaScript in 270 of 270 test cases; greedy wrapping at UAX #14 break opportunities gives 254, because Chromium's CSS wrapping also breaks after a hyphen. Breaking at UAX #14 reads better for dates and hyphenated words and would break parity, so it is not offered. **Where:** `ferrigura-text`, `wrap.rs`; the labels built on it are `ferrigura-render`, `unified/label.rs`, and the measurement of the custom renderers is `common/text.rs`.

### The reference memoizes its text measurements with colliding keys

The reference caches `calculateTextDimensions`, `wrapLabel` and `breakString` under a string built from the arguments (`${text}${fontSize}${fontWeight}${fontFamily}` and so on), and the keys of two different requests can be equal: the second request then gets the first one's result. `TextMemo` keeps the same keys for the length of one render, so the same collisions happen within a render; the reference's cache lives as long as its page, so a collision across renders is not reproduced. **Where:** `common/text.rs` (`TextMemo`).

### Embedded subsets need a family name of their own

The embedding probes draw at the Rust width when their required glyphs are embedded, also through `<img>`, where an SVG without the fonts is not pixel-identical. An uncovered character is measured with the primary face’s missing glyph, but a viewer may substitute another font. The registry exposes that missing coverage through `FontRegistry::missing_glyphs`. The fixture findings depend on these details:

- `@font-face` rules are global to an HTML page, even inside an inline SVG's `<style>`, and of two rules with the same family the later one wins. Two diagrams with different subsets under one family name broke 33 of 549 labels of the first diagram, by up to 1.8 px. Each subset therefore gets a family name that carries a 64-bit FNV-1a hash of the subset bytes and their weight and style (`fg-<16 hex digits>-sans`), so that diagrams with equal subsets share it and others cannot disturb each other.
- The bundled compatibility family groups its four styles under `@font-face` descriptors (`font-weight`, `font-style`), and a label switches style with `font-weight="700"`. Supplied designs instead get distinct embedded families, with synthetic weight and slant disabled, so each run uses the file that measured it.
- `white-space: pre` has to target `text`, not the root: Chromium computes `white-space: nowrap` for `text` even when the root says `pre`, and drops a label's leading and trailing spaces.
- `skera` does not serialize legacy `kern` tables. Passing an empty drop-table set does not preserve them. The text crate remaps OpenType format-0 kerning pairs through the subset plan, then adds the table with `write-fonts` so its checksums and directory are valid. Other legacy kerning formats are rejected at registration rather than embedded with different advances. The registry tests use a fixture with `GPOS` replaced by a single legacy pair, checking the full face and its subset.
- `skera` does not serialize CFF or CFF2 outlines. Returning its partial output would leave an OpenType font without glyph outlines. CFF/CFF2 inputs therefore embed complete, retaining their appearance and advances; their embedded data is larger than a TrueType subset. The pinned Source Code Pro test fixture covers this path.
- A subset with no covered character has no `cmap`, so the embedder handles an empty family. `skera` keeps the color tables (COLR, CPAL) and every bitmap strike of a CBDT font, which makes such faces large, and it drops the `SVG ` table, so OpenType-SVG fonts cannot be embedded with it.

For the text fixtures, about 95 characters of one face come to 9 to 12.5 KB, from 52 to 72 KB for the whole face. **Where:** `embed.rs` (`subset_face`, `embed_runs`, `fnv1a`), `tests/subsetting.rs`; the `white-space` rule is in the renderers' style sheets, for example `pie.rs`.

### WebKit measures SVG text unkerned and paints it kerned

Safari 27, WebKit 26.5 and Firefox 155 draw kerned, ligated SVG text at the Rust width, as Chromium does. But WebKit lays SVG text out from advances it measures one character at a time, so `getComputedTextLength` and `getBBox` return the sum of unkerned advances (up to 32 px more for a kerning line at 48 px), while it paints each fragment as one shaped run. Everything that derives a position from the layout width inherits the error: `text-anchor: middle` is misplaced by 17 px at 48 px, `end` by 33 px, and a `tspan` without its own `x` starts 13 px too far right. Letter-spacing, word-spacing, per-character position lists and `textLength` split the text into single characters, which makes the ink unkerned as well. None of the CSS switches changes how WebKit draws kerning.

So the labels of the unified renderer carry `text-anchor` start and an `x` computed from ferrigura's own measurement for every line, and an explicit `x` for every `tspan` that follows another; a centered label gets `x = center - width / 2`. They use neither per-character positions nor `textLength`. The browser then never derives a position from its own text width, and WebKit draws where Chromium and Firefox do. Mermaid centers labels with `text-anchor: middle`, so in Safari its SVG labels with noticeable kerning sit off center. The renderers of their own keep Mermaid's `text-anchor` for titles and many labels (`common/title.rs`, `common/draw.rs`, the sequence and gantt renderers, among others), so that kerned text there is aligned by the viewer, as in Mermaid. A check that compares widths in WebKit has to use character positions or pixels, never `getComputedTextLength` or `getBBox`. **Where:** `unified/label.rs`; the harness measures in Chromium for this reason (`tools/port/geometry/pie-geometry.ts` and `tools/port/text/chromium-fixture.ts` say so), and `crates/ferrigura-text/tests/support/mod.rs` notes it for the fixtures.

### The bundled emoji fallback uses COLRv0

The no-input compatibility path keeps its bundled fallback chain. Lexica lacks the arrows, the symbols and the emoji that diagrams use, so a missing character uses the first bundled fallback that covers it: the arrows (U+2190 to 21FF, Noto Sans Math), the text-default symbols of U+2600 to 27BF (Noto Sans Symbols 2, 252 code points) and the emoji with emoji presentation (Twemoji Mozilla, 1,185 of them). The three cover disjoint code points, so the order decides nothing among them, and a text symbol such as U+2665 is never set in the emoji face.

The emoji face is Twemoji in the COLRv0 format because that is the color format both Chromium and WebKit draw, inline and through `<img>`. COLRv1 draws only in Chromium (WebKit draws flat blocks or black silhouettes), a CBDT face is not loaded or draws blank in WebKit, and Apple's own sbix face, which is what the reference draws on macOS, cannot be bundled. Safari 27 draws the bundled text-symbol and emoji fallback faces, inline and as an image (checked in a `WKWebView` with `tools/port/fonts/webkit-snapshot.swift`); Firefox is not checked.

The visible cost: an emoji is 16 px wide at 16 px in Twemoji, where Apple Color Emoji is 20 px. The reference and Rust geometry hosts explicitly load and register the same fixture files, so those comparisons use matching coverage. The compatible bundled set covers neither 34 emoji with emoji presentation that Twemoji lacks nor the CJK, kana and Arabic text of the uncovered fixtures; the harness names an uncovered character as the reason for excluding its fixture (`tools/port/fonts/bundled.ts` reads the coverage from the files' `cmap`). The faces are cut from their sources by `pnpm -C tools/port port:cut-fonts`, which checks each source's SHA-256 first, and a second cut is byte-identical. **Where:** `measure.rs` (`fallback_runs`, `fallback_faces`), `embed.rs`, `crates/ferrigura-text/fonts` and `NOTICE.md`, `tests/emoji_and_symbols.rs`, `tests/fallback.rs`.

### The reference and renderer use the same registered fixture files

The geometry host registers the fixture files under the family aliases the reference requests, including the classic default `trebuchet ms`, cytoscape’s `Helvetica Neue`, the sequence’s `Open Sans` and the `Georgia` that configuration fixtures request. The page maps those aliases to the same files as web fonts; only the reference’s hardcoded generic sequence-number family is rewritten for its supplied-font comparison. Ferrigura resolves its supplied-font roles through the render context. The physical files also remain the no-input compatibility defaults, but the geometry host selects them through registration; `FERRIGURA_GEOMETRY_FONT=mono` selects a second primary in both hosts. The unknown icon's question mark keeps the reference's `ArialMT, Arial`, which ferrigura does not ship: the harness draws it with the machine's Arial on both sides. The reference also measures in `sans-serif` and keeps those values only when they are larger in width, height and line height at once; on macOS it kept the configured font for all 492 probed requests. **Where:** `tools/port/geometry/common.ts` (`MAPPED_FAMILIES`), `ferrigura-render`, `common/text.rs` and `tests/common_text_chromium.rs` (`the_reference_keeps_the_configured_font_for_every_probed_text`).

### Text is measured with entity placeholders and drawn decoded

The parsers see `#name;` encoded as `ﬂ°name¶ß` (`encodeEntities`), and `mermaidAPI` decodes the whole serialized SVG at the very end. Layout and wrapping therefore measure the placeholder, while the SVG shows the decoded character; the embedded font subset is cut from the decoded characters. Fixture coverage must include the internal placeholder as well as the visible text. The geometry harness conservatively scans possible entity placeholders and warns when a selected fixture face and its registered fallbacks lack a character; syntax that is never measured may also trigger a warning. A warning never changes exclusions or tolerances. Lexica covers the sentinel, but Atkinson Mono lacks U+FB02: Chromium may substitute a system face while ferrigura measures the primary missing glyph. The Mono sequence comparison with escaped line breaks therefore remains a measured difference, not a parity claim. Registering Lexica as an explicit fallback makes both hosts measure the same glyphs; it is a diagnostic control, not a change to the fixture or production fallback policy. `pnpm -C tools/port test:placeholder-coverage` checks both faces, the registered fallback and the decoded text in the pinned Chromium on macOS, and reports the actual browser fonts. A title that is sanitized as markup turns `&` into `&amp;`, which `.text()` writes as `&amp;amp;`. **Where:** `common/text.rs` (`shown_text`), the renderers' `text.rs`.

### SVG collapses white space, so subsets are cut from the collapsed text

A label `name\nvalue` in one SVG text is drawn as `name value`. A subset cut from the raw text has no space glyph, and the viewer then takes the space from another font, which moves the text by a fraction of a pixel. The text is collapsed before the subset is cut. **Where:** `common/text.rs`.

### Chromium lays text out at a floored size and on a baseline grid

Chromium lays SVG text out at its font size floored to 1/100 px, and places baselines on the 1/64 px grid: `dominant-baseline: middle` is half the x-height and `hanging` is 0.8 of the rounded ascent. **Where:** `common/text.rs` (`laid_out_size`).

## JavaScript and browser arithmetic

A layout engine amplifies the last bit of a number into positions that differ by pixels, so the numbers must match, not only the algorithm ([0012](./decisions/0012-layout-engines-ported-exactly.md)).

### V8's `Math` differs from the platform's

For the same input bits, the platform's `sin`, `cos` and `log` give another last bit than V8's for a few percent of inputs. A port that calls them has that share of its radial start coordinates one ulp away from the first placement on, and a tolerance would hide that where a zero tolerance fails. `ferrigura-jsmath` computes the functions as Chromium does:

- `sin`, `cos`, `tan`, `asin`, `acos`, `log` and `log10` are correctly rounded, by Ziv's method (256 fraction bits, rounding when both bounds agree). `sin`, `cos` and `acos` first try a double-double evaluation with a proven error bound and use it when its whole interval rounds to one double, which is the same result much faster. Chromium's results are correctly rounded on every input probed, so the two agree.
- `atan` and `atan2` are ported from llvm-libc, which Chromium's V8 takes them from; they are not correctly rounded.
- `pow` is the platform's, with V8's special cases, and `hypot` is V8's two-argument formula. Both runtimes agree on these two, and only macOS was checked for `pow`.
- The `node` module has Node 24's functions (V8's fdlibm port), because the parser differentials run in Node and Node and Chromium disagree on `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `atan2`, `log` and `log10` for 0.5 to 11 percent of inputs.

The renderer takes every one of these functions from `ferrigura_jsmath` and never from the standard library: `ferrigura-render/tests/browser_math.rs` fails on a call of any of 26 platform functions (including `powi`, whose precision Rust leaves open). A million inputs per function against Chromium are compared by `pnpm -C tools/port port:jsmath`. **Where:** `crates/ferrigura-jsmath`.

### Fused multiply-adds make some outputs depend on the architecture

V8's C++ and llvm-libc are compiled with the compiler's contraction, which fuses `a * b + c` on targets that have a fused multiply-add instruction: every aarch64 target, and x86-64 with the `fma` feature. The x86-64 baseline has none, so V8 does not contract there. The functions that depend on it are `atan`, `atan2` and Node's fdlibm functions; the correctly rounded ones and `hypot` do not. `CONTRACTS` says which way the build goes, and the samples for the dependent functions were taken on aarch64. Hence the snapshots are taken on aarch64 ([0005](./decisions/0005-quality-gates.md)), and CI checks the snapshots on an arm64 runner. **Where:** `ferrigura-jsmath`, `fused.rs`; `.github/workflows/ci.yml`.

### Numbers become text the way JavaScript writes them

`String(number)` is the shortest digits that read back as the number, in plain notation from `1e-6` up to `1e21` and in exponent notation outside that (`1.8369701987210297e-14`, `1e+21`), with both zeros as `0`. When two shortest candidates are equally near, JavaScript takes the even digit and Rust may take the other (`1708300000000000.25` is `...0.2` in JavaScript and `...0.3` in Rust), so `number_text` uses Ryū-js to preserve JavaScript’s rounding and spelling. Every number the SVG shows goes through it, or through `NumberText`, which writes the same text into a buffer. **Where:** `ferrigura-model`, `value.rs` (`number_text`, `NumberText`), checked against Node on a table written by `tools/port/number-text-table.ts`.

### Numbers are read exactly, and the browser works in float32

`serde_json`'s default float parser is not correctly rounded. The workspace enables `float_roundtrip`, so JSON numbers are read as JavaScript reads them; without it, differences of about 1e-14 showed on otherwise identical ELK cases, and a width of `14.013293266296387` read one ulp away moved a Brandes and Köpf size. `JSON.stringify` writes `-0` as `0`, so captured values are compared with `==`.

The browser side has float32 in places: `getBBox` returns float32 values, and Blink parses the numbers of a path into float32. `browser_f32` and `path_coordinate_f32` do the same, and several tests in the unified renderer fail by one float32 ulp if they do not ([SVG and Chromium geometry](#svg-and-chromium-geometry)). **Where:** the root `Cargo.toml` (`float_roundtrip`), `ferrigura-render`, `unified/geom.rs`.

### JavaScript's sort order, key order and string order are part of the result

- GWT's `Collections.sort`, which elkjs uses, is not TimSort but the legacy merge sort: insertion sort below seven elements, a shortcut when the halves are ordered, and a merge that prefers the left run. **Where:** `ferrigura-elk`, `java/sort.rs`.
- `Math.min` and `Math.max` give NaN when any operand is NaN, where `f64::min` and `f64::max` ignore it, and they distinguish signed zero. **Where:** `unified/tidy_tree.rs`; `unified/path.rs`.
- JavaScript strings are UTF-16, and lengths, slices and regular-expression positions count code units. Where a result depends on them, the code counts them too: marked's lexer masks and emphasis positions shift for an escaped character outside the Basic Multilingual Plane. **Where:** `unified/marked.rs`.

## SVG and Chromium geometry

### Reveal masks preserve an edge's dash pattern

The [draw animation](./decisions/0021-optional-svg-draw-animation.md) reveals each edge through a
separate stroked mask. Animating the original edge's dash array would replace
the neo arrowhead gaps, dotted lines, and line-hop spacing. End markers use
stroke-free carrier paths whose groups fade in on arrival, retaining the
original marker definitions. Very short `step-end` animations can finish with
progress just below 1 in Chromium because of floating-point rounding, leaving
the initial value visible under `fill: both`; a brief linear opacity fade avoids
that boundary. The end values match the static SVG properties, so backwards fill
is enough. Releasing masks and opacity effects at completion avoids differences
in rasterization from retained compositing layers. The preview checks the final
pixels against the original SVG. Export checks run the standalone SVG with
JavaScript disabled, since manually seeking an inline preview past its end can
hide a boundary failure.

Reveal masks need an easing that settles without overshooting: a dash offset
outside its reveal range can hide a completed part again. Each connection, bar,
and sector uses its own easing within a duration derived from length and speed.
Easing the entire diagram would make the boundaries between pie sectors or
successive bars pass at full speed instead of giving each one a soft finish.

### Rebuilding a loaded Node addon on macOS needs a fresh file

Overwriting a staged `.node` file while a preview process holds its previous
version can leave new Node processes killed on load, even when
`codesign --verify` accepts the file. If requiring the build output directly
works, stop the preview and stage that output through a new file followed by
an atomic rename, then restart. Replacing the staged file's inode resolves
this failure without changing the addon or its signature.

### A pie reveal mask must cover both sides of a separator

A wide arc with butt caps clips half the sector stroke at each radial border.
The border then becomes visibly thicker when the mask releases, even though the
completed chart matches static output. Tangential extensions past both arc ends,
sized from the stroke width, include the entire stroke. The browser check
compares a fully revealed isolated sector with and without its mask for both pie
and donut. A one-channel rounding difference from mask compositing is allowed;
the complete diagram still has to match static pixels exactly.

### The bounding box of a path is Blink's and Skia's, in float

`getBBox()` of an SVG path is `SkPath::computeTightBounds()` of the path that Blink's parser and `SVGPathBuilder` build: numbers are read in `float` by Blink's digit-by-digit parser, relative points become absolute, smooth curves are reflected, and an arc becomes conics from float matrices; the extremes of each curve are found in float. `ferrigura-path` ports that route. It matters for the mindmap's cloud and bang nodes, whose paths size the node, and where the force layout amplifies a one-unit difference into tens of pixels. Of 3,011 generated paths, 81 differ from Chromium, all within 0.05 px but one (0.094 px on a path 293,000 px across), because Chromium takes the macOS libm's float `sin`, `cos`, `tan` and `atan2`, which are not correctly rounded for a few inputs; the port takes the correctly rounded values, the same on every host. Mermaid's cloud and bang paths are not among the 81. The node's own `getBBox` then maps the path's box through the path's `translate`: since Chromium 158 the edges are moved in float and the width is taken again from them (Chromium 156 kept the width), which can move the width by one float ulp; on the mindmaps with every shape the force layout turned that ulp into up to 40 px (`BBox::translate_f32`). **Where:** `crates/ferrigura-path`, `tests/corpus` (written by `pnpm -C tools/port port:path-bounds`).

### Float32 values meet exact comparisons

The reference's post-processing of an ELK result tests borders exactly, so one float32 ulp in a box moves an edge end by pixels, and the shapes' sizes come from `getBBox`, which is float32. Two consequences are in the code. A sloped rectangle's height follows a rule measured in Chromium, not derived from its source: when the span of its outline is not a float32, the browser's height is one float32 above the nearest (433 outlines measured with no exception, 163 exact spans unchanged); the same rule misses on 11 of 178 and 87 of 484 inexact spans for unrelated coordinates, so other paths keep the nearest float32. And the values the renderer hands the post-processing are the float32 ones. **Where:** `unified/geom.rs` (`browser_f32`, `path_coordinate_f32`, `sloped_outline_height_f32`), `unified/elk_geometry.rs`.

### A width off the 1/64 px grid changes the text

A width that is not on the layout unit makes Chromium scale the SVG by a fraction and lay the text out at the scaled size, which moves its width by a few hundredths of a pixel. The reference's widths are on the grid because the browser measured them, so the pie's width is snapped (`layout_unit`). The comparison must also wait for the embedded faces to load before it measures. **Where:** `pie.rs`; `tools/port/geometry/common.ts` (the page waits on `document.fonts`).

### rough.js at roughness 0 is deterministic

The shapes that the reference draws with `rc.*` set `roughness: 0` and a solid fill, so their drawing is deterministic: every offset is multiplied by the roughness, the points and the control points lie on the line, and an ellipse is its sampled core. The one random part left, the divergence point of a double stroke (`0.2 + random * 0.2`), does not change the geometry, so a fixed fraction stands for it, and the geometry run compares a path sample on a jump between two sub-paths by both ends of the jump. The port is rough.js's generator and the renderer ops that these shapes reach. The `handDrawn` look is out of scope, and its fixtures are excluded. **Where:** `unified/shapes/rough.rs`.

### Chromium reads `NaN` as 0, and a detached element measures 0

An element whose geometry is `NaN` adds nothing to the root's bounding box, so it does not move the `viewBox`, while a text with `y="NaN"` still counts. A renderer that reproduces `NaN` geometry where the reference computes it has to keep that element out of the box as Chromium does. A text inside a detached element measures 0 with `getComputedTextLength()`, so a wrap that runs before the element is attached never wraps.

### Colors set through d3's `style` come back serialized by Blink

After `.style('fill', …)`, Chromium serializes a hex color as `rgb()` and converts `hsl()` in single precision (`hsl(247.5, 0%, 9.2156862745%)` becomes `rgb(24, 24, 24)`, where double precision gives 23); an `hsl()` with a `NaN` component is dropped. **Where:** `quadrant_chart/mod.rs` (`css_color`).

## The layout engines

Each engine is ported from its own sources and checked against the original on a captured corpus, with a tolerance of zero ([0012](./decisions/0012-layout-engines-ported-exactly.md)). The README of each crate has its source pin, its map to the sources and how its corpus is made: [ferrigura-elk](../crates/ferrigura-elk/README.md) and [ferrigura-cose](../crates/ferrigura-cose/README.md); the tidy tree is documented in `crates/ferrigura-render/src/unified/tidy_tree.rs`.

### ELK Layered follows elkjs, not the Java alone

Mermaid runs elkjs 0.9.3, which GWT compiled from ELK's Java, so the port follows what the compiled code does. The ELK commit is not recorded by elkjs and is inferred from the bundle; the options, defaults and enums are generated from the `*.melk` files, because the metacompiler's Java classes are not in the repository. Behavior the Java does not show cost the most time: two tries of the layer sweep share one flag because of a copied id, unset options read the defaults of Layered's `supports` table, GWT's `Random` and merge sort are not the JVM's, and elkjs mutates its input and adds `$H` identity hashes to its output. Only Layered is ported, and only the options Mermaid sets; the other algorithms fall back to Layered with a warning.

The comparison is layered on purpose. The processor trace with its logs is compared before the coordinates, so an error in the order of processors shows as a name, not as a shifted node; the corpus is backed by 1,200 random flat and 900 random compound graphs that the generators write, which reach what no fixture does; and every fix starts as a synthetic corpus case. **Where:** `crates/ferrigura-elk` and its README.

### ELK's network simplex is quadratic, and the port takes the same steps faster

ELK's `NetworkSimplex` costs the graph's size in every step: each round of `feasibleTree` searches the whole tree again, and each exchange scans every edge for the leaving and the entering edge and recomputes the postorder and every cut value. The iteration limit is the thoroughness times the number of nodes, so one run on the ten thousand nodes of a large node placement's auxiliary graph took about twenty seconds, and the design mode, which runs the method several times per layout, took minutes on the largest performance flowcharts. Where every weight is an integer, every cut value is an exact sum in any order, and the port reaches the same tree in the same order with less work: a round searches on only from the edges the move made tight, and an exchange updates the cut values on the cycle the entering edge closes (Gansner et al.), keeps the tree as parent edges and subtree sizes, searches the entering edge among the edges of the smaller component and moves that one. Every choice is Java's, and the layers come out to the bit; a unit test runs both ways on random graphs, and the snapshot manifest does not move. Other weights keep Java's way. The design mode still costs several times the default on the largest inputs: it places with network simplex where the default uses Brandes & Koepf, runs the method again for each pass of its own placement, and lays a diagram out again for a self-loop that does not fit. **Where:** `crates/ferrigura-elk/src/common/networksimplex.rs` (`grow_tight_tree`, `pivot`).

### Network simplex placement writes the sizes of resizable nodes back

`ElkGraphLayoutTransferrer` sets a node's width and height from the layout when the graph places its nodes with network simplex and the node may resize where space permits (`NODE_SIZE` or `NODE_SIZE_WHERE_SPACE_PERMITS`), as it does for size constraints and nested graphs. Without it a resized node keeps its input size. **Where:** `crates/ferrigura-elk/src/layered/transfer.rs`, `p4nodes/network_simplex.rs`.

### ELK's node flexibility is not a way to straighter edges in the design mode

With `nodeFlexibility` `NODE_SIZE`, the network simplex placement makes a node as long as straight edges need, without a limit: a node with four edges in became nearly four times as high and pushed its neighbor out of the layer's row. A flexible node also gets its ports where the edges arrive, up to the corners of the node, so the edges of a side no longer form a bundle, and a chain of nodes with one edge on each side loses its centered edges. elkjs 0.9.3 throws `NEdge must have a source and target NNode specified` for every corpus case with a self-loop once nodes are flexible; the port lays those out, and nothing says whether the result is right. Limiting the stretch from outside (naming the nodes, laying out again when one grew too far) straightened some edges and bent others. The design mode keeps every node at its size and its ports in the middle of the side. **Where:** `ferrigura-render`, `flowchart/policy.rs` (`relax`); the corpus's `ns-node` cases hold the option on single nodes.

### A short step in an edge costs a placement little and looks worst

ELK's node placements minimize the lengths of the steps of the edges. By that measure a step of ten is nearly as good as none, and where two straight edges do not fit, the placement leaves one of them with a short step, or two nodes half a port distance beside each other. A drawing reads as calm for another reason: its nodes stand on few common lines, and an edge is either straight or turns clearly. The lengths also leave ties, which the network simplex method breaks towards one end: a node with two successors stands over one of them. And ELK counts the end of a long edge for more than an edge between two nodes, so an edge that runs back to the start can take the straight line from the main flow. The design mode's placement therefore decides first which edges are axes and gives them a weight no sum of other edges reaches, counts an edge between two nodes for more than a long edge's end and an edge against the flow for less, and then moves each group of nodes on one axis into the middle of what the lengths left open. With an even number of edges on a side, no port is in the middle, so the bundle has to move by half a port distance for the nodes of an axis to stand on one line. **Where:** `ferrigura-render`, `flowchart/placement.rs` and `unified/pipeline.rs` (`own_placement`); `ferrigura-elk`, `placement.rs` for the hook.

### A labeled edge is a long edge in ELK

ELK Layered gives an edge label a dummy node in a layer of its own between the layers of the edge's ends. A labeled branch of a decision therefore passes a layer in ELK's terms, even when no node stands between its ends, and the layers ELK hands a placement hook cannot say which edges are long between nodes. The design mode's side exits judge "the next layer" by the boxes instead: no node stands between the decision and the target along the flow. ELK also routes every edge out of the side that faces the next layer, so a branch to a node beside the decision turns twice, down, across and down, and the label sits on the last part into the target, which a route out of the side tip keeps. **Where:** `ferrigura-render`, `flowchart/turns.rs`; `ferrigura-elk`, `placement.rs` (`Kind::Label`).

### ELK's self-loop is a hook with its label beyond it

ELK Layered routes a self-loop with its own processors: ports on the node, a route around them, and the label placed outside the route, on the far side of the hook. The port covers loops with one edge per pair of ports (`layered/loops`). With the free port constraints of a flowchart, a loop is a short hook near a corner and its label floats tens of units away from it. Options do not move the label next to the line, so the design mode takes the loops out of ELK's input, reserves their room in the node's box and draws them after the layout. A node in a group with a direction of its own does not always meet its edges in that direction: a member of a `direction BT` subgraph in a chart from left to right, with edges across the frame, meets them on its left and its right. The mode therefore tries the other direction's sides before it gives a loop back to ELK. **Where:** `ferrigura-render`, `unified/loops.rs`; `ferrigura-elk`, `layered/loops`.

### ELK keeps the ports of a group at the start of its side

An edge to a group with `INCLUDE_CHILDREN` meets the group at a port 12 from the start of its side (the ports' surrounding margin), whatever the group's `portAlignment` says: setting `CENTER` on the group changed nothing. Brandes & Koepf then often lines the other end up with the middle anyway; network simplex, and the design mode's placement after it, leave the edge at the group's corner. The mode's placement therefore moves every side's bundle into the middle of its node before it places anything, which is a no-op for a leaf whose ports ELK already centered. With several edges on a side, ELK spreads the ports of a group unevenly instead: the first 12 from the start, the others 20 apart near the end (12, 184 and 204 on a side 216 long), so the bundle's middle can be the side's middle while no port is. Making every such side an even bundle bent edges that ELK's spread had left straight, in groups whose edges mix directions; the mode makes only a fan of equals an even bundle. A port with an edge that crosses into the group (`Port::inside`) must not move at all: the inner layout routed the edge on from it, and a moved port leaves a slanted segment. **Where:** `ferrigura-render`, `flowchart/placement.rs` (`center_bundles`, `center_axis_ports`).

### Mermaid's ELK integration is ported as well as ELK

What Mermaid does around elkjs is part of the layout: it builds the ELK graph from the layout data (`buildElkGraphFromLayoutData`), and after the layout it applies the positions, evens group frames, clips edges to the shapes' outlines, straightens the port-to-channel jogs at the ends of routes and places terminal labels. These steps decide where an edge ends, so they are ported function for function, with their thresholds. The reference's patch 07 gives the harness each ELK input and layout (`globalThis.__mermaidElkCapture`), so the harness compares the graph ferrigura hands to ELK with the reference's before it compares any geometry: the two are equal for all 298 comparable flowchart fixtures. The Mermaid option `layout: dagre` is laid out with ELK as well; the geometry runs leave such fixtures out. **Where:** `ferrigura-render`, `unified/elk_build.rs`, `elk_apply.rs`, `elk_geometry.rs`, `elk_straighten.rs`, `terminal.rs`; [flowchart](./diagrams/flowchart.md).

### cose-bilkent is the tree path, and its edge ends are cytoscape's

A mindmap is one tree, so cose-base takes its radial path: it finds the center of the tree by peeling leaves, places the nodes on rings around it and starts the spring embedder from there. That path draws no random numbers, so the layout does not depend on the page; the random path is unreachable from Mermaid and is not ported. The source has quirks that the result depends on and that the port keeps: `findCenterOfTree` splices its list while it iterates it, which makes the center wrong for many trees (a path of five nodes gets its second node), and `branchRadialLayout` divides `(end - start + 1) / 2`.

One thing sits outside the obvious engine. cytoscape-cose-bilkent loads cose-base 1.0.3 and layout-base 1.0.2, not the 2.x versions that Mermaid's fcose uses. And the edge endpoints that Mermaid reads back (`rscratch`) are cytoscape's, for its default 30 by 30 node style, not Mermaid's box sizes: every edge end lies on a circle of radius 15 around its node's center, and the mindmap renderer reproduces that. **Where:** `crates/ferrigura-cose`, `ferrigura-render`, `mindmap/layout.rs`; [mindmap](./diagrams/mindmap.md).

### The tidy tree is a package that the bundle does not register

`layout: tidy-tree` needs the package `@mermaid-js/layout-tidy-tree` to be registered by the host page; Mermaid's own bundle does not contain it, and without it the layout quietly becomes cose-bilkent. ferrigura draws the tidy tree, so the reference for it is the registered package, built by the harness from sources vendored under `tools/port/vendor`. The layout is van der Ploeg's non-layered tidy tree on a transposed tree (the breadth of a tree is the node's height) with four quirks that the port keeps because the contract is the reference's output: the first level is centered on the tops of its nodes, the reported midpoint is not an endpoint, `mindmapCircle` is not among the round shapes, and an edge between two nodes of one side doubles back. **Where:** `ferrigura-render`, `unified/tidy_tree.rs`; [mindmap](./diagrams/mindmap.md).

## The reference and the harness

### The reference is loaded through Vite's SSR loader

The exporters run with `tsx`, but they load the reference's modules through Vite's SSR loader (`createServer` with `ssrLoadModule`), not through Node's module loader. The reference's configuration imports `config.schema.yaml?only-defaults=true`, a query that the schema plugin of the reference's `.vite/` handles and that Node and tsx cannot load. Vite runs the same plugins as the reference's tests, so the reference is loaded the way it is tested. Two details follow: the detectors must be registered before `preprocessDiagram` runs (the reference's directive handling calls `detectType`, which throws for any directive when none is registered), and DOMPurify, which the DB setters call, needs a window, so most exporters install a jsdom window before loading the reference. **Where:** `tools/port/reference.ts` (`registerDetectors`, `provideDomForSanitizing`), `reference-root.ts`; [tools/port/README.md](../tools/port/README.md).

### The page fixes the clock, the random numbers and the environment

Two renders of one text would differ in the reference: the gantt's today marker reads the clock, and rough.js strokes read `Math.random`. The harness page replaces `Date` and `Math.random` for each render with a fixed time and a mulberry32 stream from a seed, passes the time to ferrigura (`RenderOptions::now`), and runs in UTC, because the reference reads dates in the browser's time zone and ferrigura in UTC. `pnpm -C tools/port port:geometry <type> --self` renders the reference twice and fails on any difference, which finds the nondeterminism the page does not yet cover. In the parse differential, ids that the reference draws at random (the regions of a state diagram) are generated deterministically in the reference's format and replaced by placeholders in order on both sides.

The page's conditions are part of the comparison: Chromium runs with `--font-render-hinting=none`; the viewport and the screen are 1200 by 900 px and the body has no margin, so a renderer that reads the screen or its container (the gantt's `offsetWidth`) gets 1200 px, which ferrigura takes unless the configuration sets a width; `htmlLabels: false`, the explicitly registered fixture font aliases and the strict security level are forced, on both sides and also as the site configuration, because an invalid `init` directive in a fixture makes the reference drop every directive; a theme that ferrigura does not ship is replaced on both sides by the fallback, since only colors differ; fixture text is decoded as the e2e viewer decodes it (`entityDecode`); and each SVG is measured at scale 1. **Where:** `tools/port/geometry/common.ts` (`renderReference`, the page's `<style>` and `<script>`), `diagram-geometry.ts`.

### Linux and macOS Chromium lay out text differently

The geometry comparison runs on macOS: Chromium there keeps fractional glyph advances, as ferrigura's measurement does. On Linux, with hinting off, the redux themes match, but other fixtures differ (see [Open questions](#open-questions)). The parse and layout-data runs and the engines' corpora do not depend on the browser and run anywhere. **Where:** `.github/workflows/ci.yml` (the `port-geometry` job runs on `macos-latest`).

### The reference itself fails on some inputs

A fixture on which the reference throws, or draws garbage, is not a difference of ferrigura. The geometry run classes it as "reference failed" and a differential run lists it as a named exception: `layout: elk` on a mindmap crashes the reference for every mindmap, so ferrigura lays such a mindmap out with ELK and the harness does not compare it. Such a rule is written down with its reason, never skipped silently ([0014](./decisions/0014-upstream-reference-at-a-pin.md)). **Where:** `tools/port/exceptions.ts`, `geometry/diagram-geometry.ts`.

### The reference's output goes through DOMPurify, and starts with an empty group

At every security level but `loose` and `sandbox`, the reference runs DOMPurify over the finished SVG, which drops `use` elements (sequence actor icons are not drawn) and `text-height` and trims attribute values; ferrigura writes what is left. `mermaidAPI` appends an empty `<g>` before every diagram, so the renderers write `<g></g>` first, and the geometry key counts it. **Where:** `sequence/conf.rs`, `gantt/draw.rs`; the renderers' root functions.

### Configuration is read as the reference reads it, not as the schema says

`defaultConfig.ts` builds some sections from scratch, so schema defaults such as `class.padding` do not exist in the reference; the generated configuration leaves them without a default (`CLASS_KEYS_WITHOUT_DEFAULT` in `crates/ferrigura-model/build.rs`, and `RAILROAD_KEYS_WITHOUT_DEFAULT`, since the configuration covers every section of the schema). Some renderers read another type's section (class reads `state.titleTopMargin`, `useMaxWidth` and spacing), some read their style options from `themeVariables.<type>` rather than their section (`xyChart`), and the theme's variables are merged over the default theme's, so an unset variable takes the default theme's value. `port:diff config` checks the resolved result ([0008](./decisions/0008-canonical-model-and-typed-views.md)).

### The reference keeps state between renders, ferrigura does not

The reference keeps module-level state across the renders of one page (`actorCnt`, the gantt's `taskDb`, the measurement memo). ferrigura keeps none, and the exporters load a fresh DB module per input where the reference's state would leak (`tools/port/export-gantt.ts`). The default SVG id is a hash of the text and the configuration (`crates/ferrigura/src/lib.rs`, `derived_id`), so the output is deterministic, and any change to a fixture, even a `%%` comment, changes its snapshot ([0018](./decisions/0018-deterministic-output.md)).

### Integration-test artifacts can fill a hosted runner's disk

The workspace's many integration tests each link a binary. Full test debug information and incremental compilation caches can exhaust a hosted Linux runner's disk during linking, before tests run. The Rust CI job uses `CARGO_PROFILE_TEST_DEBUG=line-tables-only` to retain file/line backtraces and `CARGO_INCREMENTAL=0` because its build artifacts are not reused across jobs. Test coverage, assertions and optimization levels stay the same. **Where:** `.github/workflows/ci.yml`, `rust` job.

## The build

### Size optimization costs render time only in the layout and text crates

A release build with `opt-level = "s"` for every crate is about a third smaller than one at `opt-level = 3` and renders the corpus 78 percent slower; `"z"` is about half the size and 101 percent slower. The time goes to the crates that run in the inner loops: the layout engines (`ferrigura-elk`, `ferrigura-cose`), the browser arithmetic (`ferrigura-jsmath`, `ferrigura-path`) and the text stack (`ferrigura-text`, HarfRust, skera and the font crates). With those at 3 and every other crate at `"s"`, the corpus renders as fast as at 3 throughout (the runs differ by a percent either way), and the artifacts are 14 percent smaller than with fat LTO alone. Fat LTO in one codegen unit takes 15 percent off on its own and costs no render time; it costs build time, about four times that of a build without it. The profile does not change the SVG: the corpus renders byte for byte the same under every profile measured, so the snapshot test, which runs under the release profile, is the check when the profile changes. **Where:** `Cargo.toml`, `[profile.release]` and its package overrides.

## The porting method

What worked, in the order it was needed.

### Port the spec files first, test for test

Every spec file of the reference gets a Rust counterpart with the same test names ([0015](./decisions/0015-differential-testing.md)). The specs measure progress instead of estimating it, they hold the behavior that nobody wrote down elsewhere, and a spec that cannot pass is ignored with its reason instead of deleted, so the ignored count stays visible ([0005](./decisions/0005-quality-gates.md)). The counts are in [diagrams/](./diagrams/README.md#coverage).

### Compare at every stage

A wrong number in the parse shows as a model difference, not as a shifted node three stages later. So the stages are compared separately: the canonical model, then the layout data (`getData()`), then the layout engine's input and output, then the geometry. The layout data run for a unified-renderer type finds a `getData` difference before the geometry does, and the ELK input comparison finds a difference in the graph before the layout is blamed. The order of a trace comes before coordinates. Each comparison names the first difference, and counts differences by field.

### Run the reference's own code, and label what is known

A rule is only learned by running the reference: the built bundle in Chromium, the source with `tsx` for parser and DB code, or the libraries in `node_modules`. The reference is never reimplemented to learn what it does. In the notes of a port, each fact says how it is known: probed (the reference ran and the result was seen), read (in the source, not run) or unverified. A probe that settled a quirk becomes a test: an explicit case in `tools/port/cases.ts`, a probe under `tools/port/geometry/probes/<type>`, or a known answer in a crate's tests.

### Reproduce quirks, and name the exceptions

A quirk that changes the output is reproduced, with its probe as a test: the compatibility promise is that the same text renders the same diagram. The explicit adaptive flowchart policy has a separate comparison and preserves a Mermaid-compatible render option ([0019](./decisions/0019-adaptive-flowchart-mode.md)). Other differences are accepted only where the reference crashes or its result depends on the page (a random value, the clock), with their reason, and a bug is fixed only together with a patch on the reference ([0017](./decisions/0017-reproduce-the-reference.md)). The easy mistake is to fix a quirk because it looks like a bug.

### Port the dependency, not a substitute

Where a result depends on a library, the library is ported, and checked against the original:

- **js-yaml.** A YAML 1.2 parser disagreed with js-yaml on 8 to 13 percent of generated inputs (indentation, tabs, empty keys, flow lines), because js-yaml is not a YAML 1.2 reader in every detail. `yaml.rs` is a port of js-yaml's own loader with `JSON_SCHEMA`, state for state, with one deliberate defensive limit: because it materializes a Rust tree instead of sharing JS object references, it bounds expanded nodes, string and key bytes, and collection nesting depth per YAML document to prevent Billion Laughs expansion and stack overflow (recorded as `unsupported` entries under `yaml` in `tools/port/exceptions.ts`). `pnpm -C tools/port port:diff yaml` compares them on over 4,000 inputs.
- **marked.** Mermaid reads label Markdown with marked's lexer. The port keeps its rules, builds the patterns with the same substitutions, translates JavaScript regular expressions to Oniguruma and counts UTF-16 code units where marked does. `port:diff markdown` compares lines and words.
- **DOMPurify.** The subset that `sanitizeText` reaches is ported, and runs twice on the strict path, as the reference does: once with the defaults, then with `FORBID_TAGS: ['style']`.
- **rough.js, d3 and V8.** rough.js at roughness 0, the d3 modules the renderers use (scales, arcs, ticks, time formats, the linear line), and V8's `Math`.

**Where:** `ferrigura-syntax`, `yaml.rs` and `sanitize.rs`; `ferrigura-render`, `unified/marked.rs`, `unified/shapes/rough.rs` and `common/d3/`.

### Transcribe arithmetic, do not simplify it

Where an engine's numbers must match, the port keeps the source's expression trees and its iteration order, uses arena indices for linked structures (the tidy tree's threads and sibling lists), and returns an error where the original throws instead of panicking. Floors on corpus sizes only go up, a corpus has a manifest that a test keeps in step with its files, random generators are seeded and write outside the repository's tracked files, and each fix of an engine starts as a corpus case that fails.

## Open questions

- **Pie on Linux Chromium.** With `--font-render-hinting=none` the redux themes match the reference, but fixtures that name a classic theme (default, dark, forest, neutral), the hovered slice and the bottom legend differ by up to 0.7 px. The cause is not found; the next step is to run the comparison in Playwright's Docker image. CI compares on macOS, where all of them match.
- **Scripts the bundled faces lack.** CJK, kana, Arabic, the 34 emoji with emoji presentation that Twemoji lacks and the symbols that Noto Sans Symbols 2 lacks have to be registered by the user, and fixtures with them are not compared. Firefox is not checked for the bundled fallback faces.
- **Text measurement of the custom renderers on Linux and Windows.** The reference keeps the configured font over `sans-serif` on macOS for every probed text; the system `sans-serif` on other systems may be larger, and ferrigura measures the configured font only.
- **Other targets than macOS and aarch64.** The samples of the functions that depend on fused multiply-adds were taken on aarch64, `pow` is the platform's and was checked on macOS only, and x86-64 and Linux are checked where CI runs them.
- **Grapheme and code-unit counts.** Whether `Intl.Segmenter` and `unicode-segmentation` agree on the newest emoji sequences is not checked.
- **WOFF2.** The subsets are embedded as TTF; WOFF2 would roughly halve them, but needs an encoder that has not been evaluated.

### HTML and SVG edge-label backgrounds differ

Mermaid's HTML-label path gives the paragraph inside an edge label its own background color. The SVG-label path applies an additional opacity of 0.5 to its background rectangle. Changing `edgeLabelBackground` to an opaque color does not remove that multiplier. Ferrigura applies full opacity once in the shared edge-label painter, retaining each type's theme fill in both render modes. State otherwise repeats the same half-opacity bug as flowcharts. Reference patch 12 applies the shared correction in `createText`; patch 11 also corrects the flowchart stylesheet. Neither changes geometry. The theme color's explicit alpha channel still applies ([0019](./decisions/0019-adaptive-flowchart-mode.md)).

### Edge storage does not identify the layout container

The flowchart input stores every edge on the root. ELK imports the edge into the lowest common ancestor of its endpoints, or the parent of a self-loop. A policy based on the current `edges` array therefore applies nested labels to the wrong graph. Adaptive routing resolves that containment and the intermediate containers on both endpoint branches before deriving each parent's label-aware port spacing ([0019](./decisions/0019-adaptive-flowchart-mode.md)).

### Sequence labels inherit the embedded subset

Sequence text uses the same top-level family for actors, notes and messages. A local `font-family` declaration with the configured family overrides the root's unique embedded subset; an external SVG then falls back to the viewer's serif face. Text inherits the root family while retaining its local size and weight. The subset collects decoded entity glyphs: subsetting the parser's placeholders instead leaves literal angle brackets to a fallback font. Standalone SVG tests exercise a family unavailable to the viewer. Sequence notes do not carry `data-look="neo"`: the reference's `drawNote` does not mark them, and marking them adds an unintended shadow.

### Participant boxes do not need the glyph band

Neo sequence rows reserve a glyph band, label and two gaps for icon participants. In optimized rendering (`compat: false`), a plain participant has no glyph: its rectangle uses the measured label height plus the two label gaps. Compatibility mode keeps the original row-spanning box. The header bottom and footer top stay at the existing lifeline datum, so message positions, row height and wrapping do not move ([0019](./decisions/0019-adaptive-flowchart-mode.md)).

### Accessible descriptions and the reference

For the description `A < B & C`, Mermaid's SVG exposes the literal entity text `A &lt; B &amp; C` to an XML or HTML consumer. Ferrigura exposes `A < B & C` for pie and flowchart; the other tested types that support descriptions expose the same entity text as Mermaid. The decoded text is more readable to an accessibility consumer, but this difference is not yet recorded as an intentional compatibility decision. The standalone accessibility comparison checks both values explicitly. **Where:** `crates/ferrigura/tests/accessibility-cases.json`, `tools/port/geometry/accessibility.ts`.
