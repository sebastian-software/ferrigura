## Files

- `diff.ts` runs both sides for one type and writes the outputs and a summary to `target/port/`. A rejection on both sides counts as agreement.
- `inputs.ts` collects the inputs: the e2e fixtures, the string literals of the `.spec.ts` and `.spec.js` files that start like the diagram, the mermaid blocks of the docs, and the explicit cases of `cases.ts`. Identical texts are kept once.
- `cases.ts` holds explicit inputs the reference's tests do not cover, such as title precedence and blank handling in `accDescr` blocks. `undetectedCases` holds the inputs that the detector of their type must not take: both sides reject them, and the configuration run expects no scope for them.
- `export-flowchart-data.ts` runs the reference's `getData()` after the same steps as a render (`setDiagramConfigScope`, the directives), and writes the layout data in the names and the nulls of the Rust `LayoutData`. `diff-flowchart-data.ts` runs it, runs the `flowchart_data` example over the same input file (or on one text on stdin, for a single case) and compares the outputs field by field; the named exceptions are in `exceptions.ts` under `flowchart-data`.
- `export-timeline.ts` writes the canonical JSON of a timeline: the reference's preprocessor, the type check of `detectType`, the Jison parser and `timelineDb.js`. The header texts come from the common DB, which sanitises them, so the reference runs with a window. The model is in [`docs-port/timeline/PLAN.md`](../../docs-port/timeline/PLAN.md).
- `export-journey.ts` runs the reference's Jison parser with `parser.yy` set to the journey DB, after `preprocessDiagram` and `encodeEntities` as `Diagram.fromText` gives the text, and reads the DB in the order of the renderer (`getTasks`, then `getActors`). The header texts go through the reference's real setters, so the reference runs with a window. Each text is converted to the text the reader sees, with the reference's `decodeEntities` and a DOM parser (see `docs-port/journey/PLAN.md`, section 6).
- `export-class.ts` writes the canonical JSON of the class diagram. It runs the reference's class Jison parser with `ClassDB`, sets the front matter title with `setDiagramTitle`, and reads the DB's state. The header texts go through the real `commonDb` setters, which need the DOM from `provideDomForSanitising`. `inputs.ts` maps the class type to the `e2e/diagrams/class-diagram/` fixtures.
- `export-sequence.ts` writes the canonical JSON of the sequence DB (`sequenceDb.ts`) after the reference's `preprocessDiagram`, `encodeEntities` and the Jison parser, with the configuration steps of `mermaidAPI` (`wrap` from the directives, `htmlLabels` and `securityLevel` pinned). The DB's header setters sanitise, so they are used as they are. Its `cssSupports` answers the box colour check as Chromium does for the values a box can name, so `parseBoxData` does not fall back to jsdom's `style.color`.
- `export-state.ts` writes the canonical JSON of a state diagram from the reference's `StateDB` after the parse, as `Diagram.fromText` leaves it: `preprocessDiagram`, the detector, `encodeEntities`, the parse and the DB reads, with the DB read before `getData()` (its second `docTranslator` pass is a draw step). The one normalisation is documented there: the ids of a trailing concurrency region are random in the reference (`generateId`), so they are written as `<generated>`, with the ids built from them. `diff-config.ts` compares the `state` section of the state inputs. The state collector reads `.spec.js` files too, and filters the fixtures by the state detector.
- `export-gantt.ts` writes the canonical JSON of gantt diagrams from the reference's `gantt.jison` parser and `ganttDb.js`. Each input gets its own DB module instance (the reference's `taskDb` survives `clear()`, PLAN section 4), `TZ=UTC` is set for it by `diff.ts`, and the clock is a `Date` subclass fixed to 1010-10-10T00:00Z. A throw from the parser or from `getTasks()` is a rejection.
- `export-pie.ts` and `export-info.ts` write the canonical JSON of the TypeScript reference. They run with tsx, and `exporter.ts` holds their shared loop.
- `export-gitgraph.ts` runs the reference's gitGraph parser and DB, with the steps of `Diagram.fromText`, and reads their state. The reference draws the digits of an id that the input does not give at random, so each commit, merge or cherry-pick whose call drew them is marked `autoId`, and its id, with every parent and branch head that names it, becomes `auto#k` (k in the order of the commits) on both sides; the random values themselves are not compared.
- `export-er.ts` writes the canonical JSON of the ER diagrams: the Jison parser fills the reference's ER DB, whose header setters, subgraph titles and front-matter title are sanitised with the DOM that DOMPurify needs, so the sanitised texts are compared (`docs-port/er/PLAN.md`, section 6). The ER specs are JavaScript, so `inputs.ts` collects their literals from `.spec.js` for ER only (`specPatterns`); the e2e folder of ER is `er-diagram` (`fixtureFolders`).
- `export-config.ts` runs the steps of `mermaidAPI` for each input (site settings, reset, `preprocessDiagram`, the diagram scope, `addDirective`) and writes `getConfig()`, the scope it set and `configKeys`. `diff-config.ts` compares them with `cargo run --example config`; `config-cases.ts` holds the explicit inputs. Each input is compared in its own scope, which must be the collection's type (`flowchart` for a flowchart input). The comparison covers the top level (`theme`, `look` and `layout` resolved), `elk`, the `pie` section and the section of the input's own type. The other diagram sections are compared when their type is ported, because the reference fills them with its own generator (`.build/jsonSchema.ts`).
- `geometry/flowchart-elk-fixtures.ts` selects the flowchart fixtures that cover the ELK post-processing passes, from a capture of the reference (`--capture <dir>`, the `target/geometry/flowchart` directory of `pnpm port:geometry-flowchart --capture`), and writes them to `crates/ferrigura-render/tests/data/flowchart-elk`, where `crates/ferrigura-render/tests/flowchart_elk_apply.rs` reads them.
- `pie-header.ts` holds the pie header rules: title precedence and the two DB whitespace rules. Both the exporter and the check use it.
- `check-header.ts` runs the real pie DB setters and compares them with `pie-header.ts`, on the inputs without `&`, `<`, `>` or no-break spaces.
- `reference.ts` loads modules of the reference and registers the detectors. The ER detector is registered by `registerErDetector`, which the ER exporter and the configuration run call after `registerDetectors`.
- `status.ts` writes the status table.

## Why the reference loads through Vite SSR

The exporters run with `tsx`, but they load the reference's modules through Vite's SSR loader (`createServer` with `ssrLoadModule`), not through Node's module loader. The reason: the reference's configuration imports `packages/mermaid/src/schemas/config.schema.yaml?only-defaults=true`. The `?only-defaults` query is handled by the schema plugin in `.vite/`, which the tests also use, and Node and tsx cannot load a YAML file with that query. Vite runs the same plugins as the tests, so the reference is loaded the way it is tested.

Two details follow from that:

- Detectors must be registered before `preprocessDiagram` runs. The reference's directive handling calls `detectType`, which throws for any directive if no detector is registered. `registerDetectors` in `reference.ts` does what `mermaidAPI` does when it loads the diagrams.
- jsdom is used only by `check-header.ts`. DOMPurify, which the DB setters call, needs a window when it is loaded, so the check sets one first. The exporters never touch the DB setters for header texts, so they run without a DOM.
