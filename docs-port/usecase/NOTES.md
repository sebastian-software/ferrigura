## 0. Summary

Use case is the Chevrotain diagram of the fork: a three-mode lexer (default, JSON body, stereotype) whose rules are tried in their written order, a CST parser with GATE predicates, a visitor that turns the CST into drafts, a model builder that checks the whole diagram and publishes it atomically, a module-state DB whose `getData` feeds the unified renderer, and a renderer that runs ELK through the shared `render` and draws its own shapes (four actor glyphs, an ellipse, a business ellipse, a JSON table, the system boundary) with the shared label helpers. ### 2.2 Lexer

Matching: the token list is tried in order and the first match wins, not the longest. `longer_alt` is the exception: when the token matches and its `longer_alt` matches more text at the same offset, the longer_alt token is emitted. `Lexer.NA` tokens (`LabelText`, `Word`, tokens.ts:126-127) never match and exist as categories. `group: SKIPPED` produces no token. The order rule is confirmed by the outcomes of section 2.4 (`--o` before `--`, `x--` before an identifier), not by reading Chevrotain's source.

Modes (`parser/usecase.tokens.ts:393-400`):

| ------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------- | -------------------------------------------- |
| `defaultMode` | the list at 323-391                                                                                                      | start                            |                                              |
| `jsonBody`    | `JsonObjectLiteral` (`matchJsonObject`, 82-113), `UnclosedJsonObjectLiteral` (`/{[^]*/`, 205-210)                        | `JsonDeclarationStart` (193-197) | either token (both `pop_mode`)               |
| `stereotype`  | `StereotypeEnd` `>>`, `StereotypeText` (`matchStereotypeText`, 115-122), `UnclosedStereotypeText` `/[^\n\r]+/` (253-258) | `StereotypeStart` `<<` (238-242) | `StereotypeEnd`, or `UnclosedStereotypeText` |

Default mode, in list order (`tokens.ts` lines of the definition):

1. `WhiteSpace` `/[\t ]+/`, `group: SKIPPED` (143-147). Only space and tab are skipped.
2. `MarkdownString` (`matchMarkdownString`, 13-23, 148-153): `"` + backquote, up to the first backquote + `"`. `UnclosedMarkdownString` `/"`[^]\*/` (154-158) is in the list but the parser never accepts it.
3. `Comment` (`matchComment`, 25-43, 159-164): `%%` only if the line before it holds spaces or tabs only; runs to the line end (not skipped, so the parser sees it).
4. `NewLine` `/\r\n|\n|\r/` (165-169), not skipped.
5. `AccDescrBlock` (`matchAccDescrBlock`, 70-80, 171-176): `accDescr` `[\t ]*` `{` up to the first `}` (no nesting; may span lines); at line start only (45-56 `isIndentedLineStart`).

7. `JsonDeclarationStart` `/json[\t ]+\w+[\t ]*@[\t ]*(?={)/` (193-197), pushes `jsonBody`.
8. Keywords, each with `longer_alt: Identifier` (215-234): `usecase-beta`, `actor`, `systemBoundary`, `end`, `direction`, `TD`, `TB`, `BT`, `LR`, `RL`, `note`, `for`, `json`, `classDef`, `class`, `style`, `include` (`/i`), `extend` (`/i`), `true`, `false`. Keyword consequences: a keyword is a `Word`, which is a `LabelText` but not an `Identifier`. The grammar's `CONSUME(Identifier)` therefore rejects keywords as names, while `nodeLabel`, `edgeLabel` and `styleValue` accept them. Quoted names are the way out. Probed cases are in section 2.4.

Lexer error: a run of characters that no token matches is skipped and reported once, with its first character (`unexpected character: ->"<- at offset: 15, skipped 1 characters.`, probed). `"` alone is such an error: `PlainString` and `MarkdownString` need their closing quote.

### 2.3 Parser (`parser/usecase.parser.ts`)

- `start` (137-141): `Usecase`, `lineEnd`, `MANY(line)`. The header must end the line.
- `lineEnd` (177-179): NEWLINE or EOF. Every statement ends with `lineEnd`.
- `line` (143-152): `blankLine` | `commentLine` | `statement`, the last gated by `isStatementStart` (676-679): LA(1) is not EOF, NEWLINE or COMMENT.

### 2.5 Quirks a port must reproduce

1. **Keywords are not names.** `actor`, `end`, `note`, `for`, `class`, `classDef`, `style`, `json`, `direction`, `systemBoundary`, `include`, `extend`, `true`, `false`, `TD`, `TB`, `BT`, `LR`, `RL` and `usecase-beta` cannot be entity, actor, boundary, class or style ids. They work in label text and in style values (`Word`).
2. **`x--` and `o--` are operators** wherever they start a token. An id of exactly `x` or `o` followed by `--` is an arrow. `--o` and `--x` take a prefix of any id that starts with `o` or `x` after `--`.
3. **`<--` and `--` take the label form only with their exact image** (the `LA(0)` gate, `parser.ts:341`, `:352`): `<---` and `---` cannot be labelled. `o--` and `x--` have one image each and take the label form for any closing `--`.
4. **The label closer must match the family.** `<--` closes with `--`; `o--` and `x--` close with `--`; `--` closes with `-->`, `--`, `--o` or `--x` (`parser.ts:357-362`).
5. **`metadataAssignmentStatement` shadows the entity statement** when `@{` follows the target. A relation after such a line is a syntax error, so relations need the assignment on its own line.
6. **Metadata values** are Identifier, PLAIN_STRING, `true` or `false`. A keyword value (`type: actor`) and a number (`1.5`) fail; `1mg` passes as an Identifier.
7. **Only the first lexer error and the first parser error are reported**, and only by position. The message texts are Chevrotain's and are not reproduced by the port (section 8, question 2).
8. **`LABEL_SYMBOL` takes any run of non-printable-ASCII characters** (`tokens.ts:317-321`), so a form feed or a non-ASCII letter in a label is label text, and in a name it is a syntax error.
9. **The dead alternative in `CssIdentifier`.** Its first alternative `--[A-Z_a-z][\w-]*` (`tokens.ts:289`) starts with `--`, which `MarkerlessSolid` (`tokens.ts:266`) matches earlier in the list, so it can never match. The second alternative is live (`foo-bar`). The port may drop the dead one without a behaviour change. `Developer --important--> WriteCode` is a label form, not a css identifier (`usecase.spec.ts:227-232`).
10. **Unquoted label text is the source slice**, including inner spacing (`visitor.ts:340-344`), and leading or trailing spacing is excluded only because the tokens start and end on label characters.
11. **Quoted names are the only way to use keywords or non-ASCII as ids.** Their id is `label.replace(/\W/g, '_')` (`visitor.ts:876-878`), so `"Café"` is `Caf_` and `"Hello World!"` is `Hello_World_`. A later bare `Hello_World_` then collides with it (probed, DB error).

### 2.6 Grammar summary for the port

The port's recursive descent follows the rule tree of section 2.3, with the same choice order. The few places where Chevrotain's LL(k) lookahead decides a choice are the `statement` alternatives (section 2.3, the GATE order) and the OPTION guards of `relationTail` and `entityName`. The port can reproduce each by trying the alternatives in order, with the GATE as the first test. Chevrotain's self-analysis raised no ambiguity error for the `statement` alternatives, although `metadataAssignmentStatement` and `entityStatement` both begin with an Identifier and `@{`; the GATE decides (probed: `UC1 @{…} --> UC2` is an error).

With `htmlLabels` true, `sanitizeMore` (`common.ts:56-69`) also rewrites `<` and `>` and `=` at the `securityLevel` in force; the harness uses `htmlLabels: false`, which skips it.
- `generateId` (`visitor.ts:876-878`) replaces each UTF-16 code unit that is not `\w` with `_`: `"Café"` gives `Caf_`, `"<b>Hi</b> & there"` gives `_b_Hi__b____there`, `"Hello World!"` gives `Hello_World_`.
- The sanitised label of a node is what `getData` writes (`label: sanitize(actor.label)`), and the note target label is the actor's raw label, sanitised (`usecaseDb.ts:402-407`).

### 6.5 Labels, escaping and accessibility

- **Plain labels.** For `labelType: 'text'`, `escapePlainLabel` (`usecaseRenderer.ts:86-88`) turns `&`, `<` and `>` into entities: node labels (109-111), stereotypes (112-114), JSON keys and values (116-120) and edge labels (137-139). Markdown labels pass unchanged.
- **Stereotype fold** (122-134). For a use case in the `ellipse` or `rect` shape with a stereotype, the label becomes `«<escaped stereotype>»<br/>` followed by the label, with `labelType` `markdown`, and the stereotype is removed from the node. A `usecaseBusiness` use case is not folded: it keeps its own stereotype label (`usecaseBusiness.ts:64`). The Markdown markers `*`, `[`, `]`, `\`, `_` and backquote are backslash-escaped in both parts (`escapeMarkdownMarkers`, 89). This uses the Markdown label path, so the port's Markdown rendering (decision 0004, Ferromark) is on the stereotype's line. Actors keep the stereotype as their own label (`usecaseActor.ts:199-207`).
- **Encoded entities.** The text reaching the renderer still has the placeholders of `encodeEntities` (section 3.7). The shared `createText` decodes them (`createText.ts`, not traced for this note; open).
- **Accessible names.** `getAccessibleLabel` (`usecaseRenderer.ts:37-44`) turns a Markdown label into lines of words with `markdownToLines` (`handle-markdown-text.ts:46`) and joins them with spaces and newlines. Actor names are `[business ][variant ]actor <label>[, stereotype <s>]`, use cases `[business ]use case <label>[, stereotype <s>]`, notes `Note for <target>: <label>`, JSON tables `<label>: <key>: <value>; …`, boundaries `<type> system boundary <label>`, relationships `association <label> from <source> to <target>` (association with a label) or `<type> from <source> to <target>` (46-84). Probed: `use case Log in`, `Note for User: Remember`.

### 6.7 Stylesheet (`styles.ts`)

`getStyles` (`styles.ts:189-396`) returns CSS that `compileCSS` scopes under the diagram's `#id` (`mermaidAPI.ts:322-330`). Its input is `{ ...config.themeVariables, theme, look }` (`mermaidAPI.ts:327-331`). It has two parts:

- `genColor` (75-187): under a colour theme with a palette (`isColorTheme`, `colorThemeGate.ts:37-38`), one rule per palette slot for system boundaries, always (`:115-124`), and for actors and use cases only when `usecase.colorScheme` is `rotate` (`:86`, `:126-186`). ### 6.9 Randomness, clock and handDrawn

- No code in the usecase files uses `Math.random` or `Date`.
- **handDrawn** (`look: handDrawn`, the fixture `complete-hand-drawn-rendering-contract.mmd`, and the `if (node.look === 'handDrawn')` branches in `usecaseActor.ts:90, 113`, `usecaseActorIcon.ts:19`, `usecaseEllipse.ts:33`, `usecaseBusiness.ts:89`, `usecaseJsonTable.ts:123`, `clusters.js:742`) draws with roughjs 4.6.6. roughjs takes a Park-Miller generator for a non-zero seed and `Math.random()` for seed 0 (`roughjs/bin/math.js:1-17`). `handDrawnSeed` defaults to 0 (schema 71-75), so the default draws from `Math.random`.

The reference is therefore deterministic under the harness, and the port cannot reproduce its numbers without that generator and the order of its draws.

## 8. Risks, effort, open questions

### 8.1 Risks

1. **The lexer and the parser are the spec, and they are order-sensitive.** The rule order of section 2.2, the first-match semantics, the `LA(0)` gates and the `statement` choice decide what parses (section 2.4 tabulates 67 probed inputs). A port that passes the spec blocks can still differ on the operators. Mitigation: run the differential on the probe inputs of section 2.4 as well as the spec inputs, and on the 32 fixtures.
2. **The model checks.** About 40 checks throw, and their order decides which error a diagram reports. A success/failure differential does not see the order; a message differential does (open question 2).
3. **Text measurement.** Every node size comes from a measured label (section 6.3). The label boxes of SVG text must follow decision 0005 (advance and glyph boxes, probed for the other types), and the Markdown labels (stereotype fold, `markdown` labels, accessible names) go through `markdownToLines` and the Markdown path. The four actor glyphs and the business marker are fixed-geometry paths, computed with `Math.cos` and `Math.sin` (`usecaseActor.ts:35-42`) and `Math.sqrt` (`usecaseActor.ts:40`, `usecaseBusiness.ts:80-81`). `sqrt` is exact in IEEE arithmetic; `sin` and `cos` need the V8 rule of P2.
4. **JSON.** The row values use JavaScript number-to-string (`Infinity`, `-0` as `0`, shortest round-trip digits, exponent forms, integers rounded past 2^53) and first-position, last-value duplicates (section 3.6). `serde_json`'s default number formatting is not the same; the port needs its own formatter.
5. **Entity placeholders.** The `encodeEntities` placeholders (`ﬂ°…¶ß`) must reach the label and be decoded at the same point as the reference, or labels with `#…;` differ. The decoding is in the shared `createText` path, which this note did not trace (section 6.5).
6. **The default `htmlLabels: true`.** The reference renders HTML labels by default; decision 0004 does not. The harness forces `htmlLabels: false`, so the fixtures compare SVG text, but a user's default render differs from the reference's default render. This is accepted by decision 0004, and the note records it so that the coordinator can confirm (question 5).
7. **Layouts beyond ELK.** `layout:` is honoured for every registered name (`render.ts:31-74`). The P2 ports cover `cose-bilkent`; `swimlane` belongs to the swimlanes research. Fixtures use `elk` only, so the risk is the public API, not the tests (question 3).
8. **handDrawn.** The reference's default draws from `Math.random` (`roughjs/bin/math.js:1-17`), and the harness pins it per render. A port that is not going to reproduce roughjs must exclude the look with the existing reason (section 7).
9. **Per-diagram appearance layer.** `look` and `theme` have per-diagram defaults that sit between the site configuration and the global defaults (`config.ts:72-118`). A typed view of decision 0009 that reads only the global values gives `classic` for a usecase diagram, where the reference gives `neo`. This must be modelled (question 6).
10. **DOM passes after the layout.** `annotateUsecaseElements` and the root `viewBox` need the final measured tree (section 6.1, steps 9-11). A port that writes attributes at emission time must emit the same ones in the same order.
11. **Shared code.** The usecase shapes depend on `labelHelper`, `createText`, `insertLabel`, `updateNodeBounds`, the note shape and the ELK layout. Changes to these by the other type ports must keep the usecase geometry (the harness will show it).

### 8.3 Open questions for the coordinator

1. **The AST.** `usecaseAst.ts` (177 lines) builds a `GraphAST` on every parse (`usecaseDb.ts:79`, `usecaseModelBuilder.ts:352`), and three specs test it (`usecase.parser.spec.ts:118, 143`, `usecaseDb.spec.ts:75`). It is not read by the renderer. Recommendation: port it with the model, because the specs check it and an editor reads it. The alternative is to leave it out with a named reason and drop the three assertions.
2. **Error messages.** Chevrotain's messages (`Expecting: one of these possible Token sequences …`) cannot be reproduced without its lookahead tables, and the DB's messages carry positions and labels. Recommendation: the differential compares whether a diagram fails, and the port's own messages are checked by the specs only; as for kanban, the Chevrotain text is not compared. Please confirm, since the P3 plan does not say.
3. **Layouts.** Should `layout:` on a use case accept `cose-bilkent` (ported in P2) and `swimlane` (P3, swimlanes research), or only the ELK names with the fallback to `elk`? The fixtures do not need the choice. Recommendation: the ELK names and `elk` as the fallback first, and `cose-bilkent` once its port exists, since the reference accepts it.
4. **handDrawn.** Port roughjs (not in the plan), or keep the harness's exclusion of `look: handDrawn` with its reason and leave the branches of section 6.6 unported? Recommendation: keep the exclusion, since the reference's default draws from `Math.random`.
5. **`htmlLabels`.** Confirm that the port ignores `htmlLabels` for use cases, as decision 0004 says. This makes the default render differ from the reference's default render, as the other types already do.
6. **Per-diagram defaults in the typed views.** The `look` default `neo` and the `theme` default `redux-color` of the usecase section are per-diagram defaults (`config.ts:72-118`). Decision 0009's typed views must keep that layer, or the port renders with the global `classic` look. Please confirm that the views of issue #4 include the layer.
7. **The `usecase.look` and `usecase.theme` keys themselves** are read only through that layer (section 6.8); the usecase code reads neither. Confirm that the typed section need not carry them as fields of its own.
8. **The docs samples.** `usecase.docs.spec.ts` checks the 24 blocks of `docs/syntax/usecase.md`. Recommendation: include them in the port's spec list, as the cheapest coverage of the syntax as written.
9. **Fixture 10 and the font mapping.** `usecaseFontFamily: Georgia` is not mapped by the harness (section 7). Either add `Georgia` to `MAPPED_FAMILIES` with the decision-0005 rule, or exclude the fixture with that reason. The choice belongs to the harness owner.
10. **The ELK options** that the usecase code sets through `nodeSpacing` and `rankSpacing` (section 6.4) must be traced in the ELK note before the renderer is written.
