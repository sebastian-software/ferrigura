# TREE VIEW parser and DB: plan and decisions

The parser task of `treeView-beta` (P3). The research, with its sources and probes, is in [NOTES.md](./NOTES.md). This page records what the port does, the decisions it took, the probes it ran, and every quirk of the reference that it reproduces, each with the test that pins it. The parser is `crates/ferrigura-syntax/src/tree_view/` (box-drawing preprocessor, scanner, grammar, DB), the model is `crates/ferrigura-model/src/tree_view.rs`, the exporter is [`tools/port/export-treeView.ts`](../../tools/port/export-treeView.ts), and the specs are `crates/ferrigura-syntax/tests/tree_view_*.rs`.

The reference is the grammar `packages/parser/src/language/treeView/` with Langium 4.4.0, the box-drawing preprocessor `packages/mermaid/src/diagrams/treeView/boxDrawingPreprocessor.ts`, and the DB `db.ts` with `parser.ts`. The decision to write the parser by hand is [0002](../decisions/0002-hand-written-parsers.md).

The exporter is named `export-treeView.ts`, not `export-tree-view.ts`: `pnpm port:diff` loads `export-<key>.ts` with the key of the type (`treeView`), as it does for `gitgraph` and `quadrantChart`.

## 1. Scope

The parser task covers the preprocessing the type needs, the grammar, the DB with its sanitising and defaults, the model, the exporter, the specs and the configuration comparison. The layout, the drawing, the icon resolution, the styles and the text measurement are the renderer stage, sections 6 and 8 of NOTES.md, and the renderer waits for issue #4.

## 2. The lexer

Langium 4.4.0 builds the lexer with `DefaultTokenBuilder.buildTokens`: the keyword first, then the terminals in declaration order, the hidden ones included. The scanner in `scanner.rs` follows that order, and each terminal's regex is one function there:

1. `treeView-beta`, with the word-end suffix `(?:(?=%%)|(?!\S))`. Its `LONGER_ALT` is `BARE_NAME`: a longer word at the same position wins, so `treeView-beta foo` and `treeView-beta  ` are one name, and the parser rejects them.
2. `ACC_DESCR`, `ACC_TITLE`, `TITLE`, `CLASS_ANNOTATION`, `ICON_ANNOTATION`, `DESC_ANNOTATION`, `INDENTATION`, `QUOTED_NAME`.
3. `WS` never matches, since `INDENTATION` takes every run of blanks before it. `ML_COMMENT` (`%%` and the rest of the line) and `NL` (`\r?\n`) are hidden, so the parser does not see them.
4. `BARE_NAME`, last.

Consequences the port keeps:

- The first pattern that matches wins, not the longest. A word that starts with `title` lexes as `TITLE` whatever follows (Q1). `TITLE` matches `title` alone.
- A blank run that is followed by `:::name`, `icon(` or `##` ends a bare name, and the annotation follows. Any other blank run stays in the name, and trailing blanks are trimmed from it. The scan tests a blank run once, which keeps it linear.
- `QUOTED_NAME` is `"[^"]*"`: it may span line breaks (Q8).
- A line of blanks is an `INDENTATION` that the next node takes (Q4).

## 3. The grammar

`grammar.rs` reads the tokens with one function per rule:

```text
TreeView:  'treeView-beta' (ACC_DESCR | ACC_TITLE | TITLE)* TreeNode*
TreeNode:  INDENTATION? (QUOTED_NAME | BARE_NAME) (CLASS | ICON | DESC)*
```

The header terminals are read before the first node, and each one assigns its property, so the last value wins, even an empty one (Q14). The annotations work the same way (Q10b). A token the grammar does not take is an error, and the reference rejects the diagram too.

## 4. The core steps and the box-drawing input

The text goes through the core as `Diagram.fromText` gives it: `prepare` (line breaks, the quotes of HTML attributes, front matter), `remove_directives`, `cleanup_comments`, `encode_entities` and a line break. Then `preprocess_box_drawing` runs, then the grammar.

Two points of this part are the port's own:

- **`cleanupComments` and U+2028.** The reference's `cleanupComments` is `^\s*%%(?!{)[^\n]+\n?` with the multi-line flag, and in JavaScript `^` with that flag matches after U+2028 and U+2029 as well as after a line feed. A `%%` comment that follows a line separator inside a line is therefore removed with its line feed (Q20). The shared `cleanup_comments` in `preprocess.rs` looked only after a line feed; it now looks after every line terminator. This is a change to a shared file, and it applies to every type that calls `cleanup_comments`. The differential runs of those types after the change are in section 9.
- **Box-drawing.** `boxDrawingPreprocessor.ts` is ported line by line. The keyword line is the first line whose trimmed text is `treeView-beta`. Box mode is on when a content line has a box-drawing character anywhere, and then the lines are rewritten: a branch line is indented by four spaces times `Math.round(column / segmentWidth) + 1`, the columns are UTF-16 offsets (so an astral character counts as two, Q21), decoration lines are dropped, and the other lines keep their text, tabs included. The map from output lines to original lines is kept, and a grammar error is reported at the original line. The two errors keep their wording, which the spec asserts: `Line N: Empty node — expected a filename or directory name after the box-drawing prefix` and `Line N: Unexpected indentation without box-drawing characters. In box-drawing format, use ├── or └── prefixes for indented nodes.`, reported at line N. The reference throws them before its parser, so they win over a lexer error on an earlier line.

## 5. The DB

`db.rs` mirrors `db.ts`, with one difference of form. The reference keeps the children in the nodes as they are added, and its stack is the chain of open nodes; here a node is appended to its parent when it is popped. The order is the same, because at most one child of a node is open at a time and the open chain has strictly growing levels.

- **The root.** The DB starts with the synthetic root `/` at level -1, id 0, a directory with no children (`db.ts:22-33`). It is never popped, and the model's `root` is always this node (Q1 of section 8.3; R1 of section 6.11). A diagram with no node is the root alone, with `count` 1.
- **`addNode`.** Pops while `level <= top.level`, takes the next counter as its id (the counter starts at 1), then becomes the child of the top.
- **`populate`.** The header texts are set when they are not empty (`populateCommonDb`), then one `addNode` per node in text order. A title is the grammar's value when it is not empty and the front matter's otherwise (Q14). A name that ends with `/` is a directory with that one slash removed (Q9). `icon()` and `icon(none)` give `none`, an absent icon is `""`, and a description is sanitised when it is not empty.
- **Sanitising.** The title, the accessible title and description, and the description of a node go through `sanitize_text`, the DOMPurify subset of the flowchart (Q13). The accessible title loses its leading blanks, and the accessible description loses the blanks after each line break, as the setters do. Names are not sanitised (Q13c), and the placeholders of `encodeEntities` stay in names and descriptions (Q12).

## 6. The model and the exporter

The model is the DB after the parse, in camelCase, as [canonical-model.md](../canonical-model.md) describes it (section "Tree view"). The fields are `version`, `title`, `accTitle`, `accDescr`, `count` (`getCount()`, the nodes plus one), and `root`, a node of `{id, level, name, nodeType, icon, cssClass, description, children}`. The exporter reads the same fields from the reference's DB after `Diagram.fromText`'s steps, with the DOM that DOMPurify needs, and the canonical example writes the Rust model. Left out: `BBox` (the renderer's), the configuration (checked by `pnpm port:diff config`), the directives, and the front matter except its title.

## 7. The configuration

`treeView` leaves `NOT_PORTED_SECTIONS` in `tools/port/diff-config.ts`, so the treeView section is compared for the 176 treeView inputs; the result is no difference. The configuration types come from the schema, as before.

## 8. The probes and the decisions they settled

Every probe below is in `cases.ts` (the explicit cases of `treeView`), so the differential runs it on the reference.

- **Probes.** The probe material of NOTES.md (`cases-parse.json`, `cases-2.json`, `cases-q15.json`, `cases-title.json` in the scratchpad) became 105 cases, and the four quirks it did not cover became cases of their own (`a :::cls extra`, a quoted name across a line break, consecutive spaces without an emoji, a tab with spaces).
- **Consecutive spaces.** The only fixture with consecutive spaces holds an emoji and is excluded by the harness (NOTES section 7). The port's test `q5_consecutive_spaces_in_names_without_emoji_are_kept` covers the rule without an emoji, and `q19_a_name_keeps_both_runs_of_spaces_and_its_unicode` keeps both runs with a non-ASCII name.
- **Errors.** The differential compares acceptance only. The Rust errors carry a position and their own message (decision 0002), except the two box-drawing messages, which keep their wording.

### The `themeVariables.treeView` probe

The question was whether `themeVariables.treeView` is honoured from a directive or only from front matter. The probe builds the style options the way `createUserStyles` does (`{ ...config.themeVariables, theme, look }`), after `Diagram.fromText`'s steps, and calls the reference's `getStyles` for `treeView`, which compiles the sheet with the reference's `compileCSS`. The probe ran in the scratchpad (`tv-theme/probe-theme.mts`), not in the repository.

Result: **honoured from both forms.** Front matter (`config: themeVariables: treeView: labelColor`) and the init directive (`%%{init: {"themeVariables": {"treeView": {…}}}}%%`) give the same compiled rule: `.treeView-node-label{font-size:16px;fill:#FF0000;white-space:pre;}` for `labelColor: '#FF0000'`, and `font-size:20px` for `labelFontSize: '20px'`, in either form. The theme (`default`, `dark`, `base`) does not change this. The finding in NOTES section 6.9 (the directive form "did not change the sheet") is not reproduced by this probe. Its cause is not known; the render harness that produced it was not run again. The renderer stage reads `themeVariables.treeView` from the effective configuration, in both forms.

## 12. The renderer stage

The renderer is `crates/ferrigura-render/src/tree_view/` (`mod.rs`: the rows, the phases and the elements; `icons.rs`: the icon of a node and its markup; `style.rs`: the options and the rules). The four questions the parser stage left for it are settled as follows.

- **The icons.** The built-in `folder` and `file` bodies are drawn; the unknown icon is the reference's 80 by 80 fallback with its `?` in `ArialMT, Arial`. ferrigura registers no icon pack, so an icon name other than the two built-ins draws the unknown icon, which the reference draws for a pack it cannot load. The `showIcons`, `filenameIcons` and `extensionIcons` rules are `icons.ts` 40-100 (section 13 has the details).
- **The labels.** The label's box is `ferrigura-text`'s box in the regular, bold (a directory, or the class `treeView-node-dir`) or italic (the class `treeView-node-description`) face, measured on the placeholder, not the character (NOTES 6.3).
- **The first CSS rule.** NOTES 6.7 and R12 read the first rule of the sheet without the svg id. That came from calling `getStyles` directly. The sheet of a real render scopes every rule, as the captured SVGs of the fixtures show, so nothing is reproduced.
- **The `themeVariables.treeView` keys.** Read from the effective configuration, in both forms (section 8). The probe `p09-theme-variables-in-a-directive.mmd` changes the label size on both sides, so the directive form is honoured.

## 13. Renderer decisions and open questions

Checked by `pnpm port:geometry treeView`: the 13 comparable fixtures and the 17 probes of `tools/port/geometry/probes/treeView` (p01 to p17, one per quirk and per branch of the arithmetic) are within tolerance, most of them exactly. The two emoji fixtures are excluded with the harness's reason (no fallback font). `pnpm port:diff treeView`, `config` and `theme` show no difference.

- **The rows.** Each row is a text box with its padding, and the rows stack. The description column is the widest label's right edge plus 16 for every row. Each highlight is sized to the tree's width at its turn, from the reference's `totalWidth - BBox.x + 8`, and widens the tree to `x + width + 2`; the reference's own numbers for the class annotations fixture are the test.
- **The icon of a file under a map.** `icon(none)`, an explicit icon, and the maps (`filenameIcons` first, then `extensionIcons` with the dot and then without it, the last dot only, and a dot that is not the first character) follow `getNodeIcon`. A falsy filename value falls through to the extension; a falsy extension value gives the default icon.
- **Errors the reference raises.** A map value that is truthy and not text, and a file name that reads an `Object.prototype` member (`constructor`, `toString`, ...), fail the render, as `qualifyIcon` fails on them (`icons.ts` 58-66). The render fails; the message is the port's own (decision 0002).
- **Open: the configuration layer.** The typed configuration reads a map entry that is not text as the schema's default before the renderer sees it, so a facade render of `extensionIcons: { .ts: 5 }` draws the default icon, where the reference fails. The renderer gets the typed section and cannot see the value; the test of the error builds the section directly. The config layer's owner decides.
- **Open: sizes.** `labelFontSize` in a unit other than pixels (or without a unit, which CSS ignores) is `RenderError::Unsupported`, since the port measures pixels only. No fixture or probe uses another unit.
- **Open: colours.** The colours are custom properties on the id and presentation attributes, as the packet renderer writes them (decision 0007). A colour value that holds a `;` or a `}` means something else in the reference, which writes the value into the rule as it is. No fixture has one.
- **Open: names.** Tabs, and names that span lines (a quoted name across a line break, Q8), are not probed. A name with a `white-space: pre` line break is drawn by Chromium in a way the port has not measured.
- **Open: the ignored tests of other crates.** `crates/ferrigura-syntax/tests/tree_view_icons_spec.rs` (23 ignored placeholders) and the `getConfig` case of `tree_view_db_spec.rs` are ported and pass in `crates/ferrigura-render/tests/tree_view_icons_spec.rs` and `tree_view_render_spec.rs`; the placeholders in the syntax crate are left for the coordinator to remove.
