## M2 handover

Stage A (configuration, text, YAML) is accepted and on main. Stage B (themes, pie renderer, geometry comparison) is done for pie: the two shipped themes are ported and match the reference exactly; the pie renderer and the `render(text, config)` facade are on the branch; the geometry comparison passes for all 24 pie fixtures. Stage C (CLI, Node addon) is done; see below.

Stage B, done: `crates/ferrigura-model/src/theme/` ports the khroma functions the themes use and the two shipped themes, `redux-color` and `redux-dark-color`, in the order of the reference. `pnpm port:diff theme` runs 110 cases (55 override sets for each theme) against the reference: no difference. The configuration takes its `themeVariables` from the theme, computed as `updateCurrentConfig` does, and `pnpm port:diff config` covers them for the two shipped themes. `crates/ferrigura-render` lays out and writes a pie as `pieRenderer.ts` does (slices with d3 angles, the legend in its four positions, the title, the viewBox), with label widths from `ferrigura-text`; `crates/ferrigura` offers `render(text, config) → svg`. `tools/port/geometry/pie-geometry.ts` runs the reference in Chromium (`htmlLabels: false`, Lexica as a web font, redux-color) and ferrigura over the 24 pie fixtures and compares the geometry in one Chromium page. All 24 are within tolerance; the largest deviation is 0.016 px, one layout unit of 1/64 px, against the 0.05 px tolerance, and the angles agree within 1e-5 rad (d3-path writes three decimals). Side-by-side images for review: the notes folder, `stage-b/pie-geometry/`. Two things found on the way: a width that is off the 1/64 px grid makes Chromium scale the SVG and lay out its text at the scaled size, so the pie width is snapped to the grid; and the comparison must wait for the embedded faces to load.

Colours, scope and accessibility (decision 0007), done. Every colour of the pie SVG is a custom property declared on the diagram's own id (`#id{--pie1: …}`), and the rules refer to it with `var()`. Each element also carries its concrete colour as a presentation attribute, which is what a viewer without custom properties draws. No element sets a colour inline. `ColorScheme::Auto` writes the light set and the dark set, the dark one under `@media (prefers-color-scheme: dark)`; `Light` and `Dark` write one set. The user's `themeVariables` apply to both sets. Every diagram has an id: by default a 64-bit FNV-1a hash of the text and the configuration, so the same input gives the same id; `RenderOptions::id` overrides it and must be a CSS identifier. Every selector starts with `#id`. `pnpm port:scope-pie` inlines three pies with different ids in one Chromium page, under a host stylesheet that paints every path, text and rectangle, and checks the computed colours of each against its declared ones under light, under dark and with the style sheets off: nine checks, all match. `accTitle` and `accDescr` are written as `<title>` and `<desc>`, the first children of the root, and the root refers to them with `aria-labelledby` and `aria-describedby`, as `addSVGa11yTitleDescription` does; `crates/ferrigura-render/src/a11y.rs` carries the cases of `accessibility.spec.ts`. Renderer rule: the pie's viewBox width is snapped to the 1/64 px grid (see Stage B). After these changes `pnpm port:geometry-pie` still passes for all 24 fixtures, and `pnpm port:diff` for pie, info, config, yaml and theme reports no difference.

Theme names: `redux-color` and `redux-dark-color` ship. Any other name falls back by darkness (names ending in `dark` take `redux-dark-color`, the rest `redux-color`), so the reference's `default`, `forest`, `neutral` and `dark` themes are drawn with one of the two. The configuration differential therefore compares theme variables only for the two shipped themes.

Known gaps for M2: the empty pie (no sections) gives the reference a `-Infinity` legend width and a broken viewBox, and ferrigura keeps zero. This is a named exception: the reference has no meaningful geometry for it to compare with. Fallback fonts for scripts Lexica does not cover; `info` is not rendered; the `default` theme of the reference is not drawn with its own variables.

Stage C, done. `crates/ferrigura-cli` builds the binary `ferrigura`: it reads the diagrams from files or from standard input, through one `Renderer`, and writes each SVG to standard output, to `--output` (one input) or to a file per input in `--output-dir`; `--config` takes the configuration as a JSON object, and `--id` and `--scheme` (light, dark, auto) are the options of `render_with`. Exit code 1 for a diagram or configuration that does not render, 2 for a command line that does not parse; 14 unit and 14 integration tests. `crates/ferrigura-node` is the napi-rs addon, Node only, with no WebAssembly build: `render(text, config?, options?)` takes the same options, and `Renderer` (`new Renderer(config?)`, then `render(text, options?)`) resolves the configuration once; errors are thrown with the crate's message. `node --test crates/ferrigura-node/test/render.test.mjs` builds the library and loads it with `process.dlopen`: eleven tests. Still open for publishing: the package layout (`index.js`, the npm name `ferrigura`, prebuilt binaries per platform), which the addon does not need to work.

Configuration, done: `crates/ferrigura-model/build.rs` generates the configuration types, their defaults and `CONFIG_KEYS` from `packages/mermaid/src/schemas/config.schema.yaml`, so the schema stays the single source. `src/config/ts_defaults.json` holds the TypeScript-only defaults (`pie.useWidth`, `treemap`); `src/config/ts_keys.txt` lists the keys the reference accepts that the schema does not name, which are the theme variables of the default theme and the TypeScript-only sections. `ferrigura_model::config::effective` applies the layers in the order of `mermaidAPI` (site config, front matter, directives; `assignWithDepth`, the key gating of `sanitizeDirective`, the removal of secure keys, the resolution of `theme`, `look` and `layout` through the diagram section). `ferrigura_syntax::config::read` reads the front matter `config` block (through `yaml.rs`) and the `init`, `initialize` and `wrap` directives, with the reference's error behaviour: invalid JSON in any directive drops all of them, and an init directive with truthy arguments (or two init directives) in a text with no detectable diagram type is an error, as `detectInit` calls `detectType`, which throws; the parser differentials reject such texts on both sides already (`undetectedCases.pie`).

Verified: `pnpm port:diff config` runs 120 inputs (the 87 pie inputs and 33 explicit cases in `tools/port/config-cases.ts`) through the reference's steps and through ferrigura: no difference, and the key sets are equal. `pnpm port:diff pie` and `info` still report no difference.

Compared: the top level and the `pie` section. The other diagram sections are compared when their type is ported, for two reasons: the reference fills them with its own generator (`.build/jsonSchema.ts`, which applies a section's own defaults only), and `defaultConfig.ts` replaces some sections whole. Ferrigura takes their defaults from the schema, so for example `class` and `railroad` carry defaults that the reference does not give them. `dompurifyConfig` is not a key in the reference and is left out of `CONFIG_KEYS`; `$ref` is left out of the comparison (a leftover of the generator in `xyChart`). M5 (T8) adds the flowchart: `pnpm port:diff config` runs its 558 inputs in the `flowchart` scope, with the `flowchart` and `elk` sections, and finds no difference once build.rs takes object defaults from the schema (`flowchart.subGraphTitleMargin`). `typed` now reads a value of the wrong type as the reference does, a numeric string as its number and anything else as the option's default, and reports each one (`config/lenient.rs`).

Specs: the pie `get_config` spec is ported and passes. `set_config` and `reset_config` stay ignored, because they are `it.todo` in the reference with their bodies commented out, and the pie DB has no `setConfig`.

YAML, done: `crates/ferrigura-syntax/src/yaml.rs` is a port of js-yaml 4's own loader (`lib/loader.js`) with `JSON_SCHEMA`, state for state: its indentation, tab, flow, block scalar and anchor rules, its errors, and the typing of plain scalars, string keys, duplicate keys, extra documents, unresolvable core tags and `undefined` for a stream without a document. The earlier reader took the structure from `saphyr-parser`, a YAML 1.2 parser, which disagreed with js-yaml on 8 to 13 % of generated inputs (indentation, tabs, empty keys, flow lines); `saphyr-parser` is no longer a dependency. A collection is shared while it is read, so an alias to an open collection sees its later entries, as in js-yaml; a lone surrogate (a `\u` escape of one) is read as U+FFFD, which the reference's UTF-8 output writes too, and the differential compares the reference's strings after `toWellFormed`. `pnpm port:diff yaml` runs 4441 inputs: the front matter of the e2e fixtures (2073, all accepted by js-yaml), the flowchart shape data of the fixtures and of the flowchart specs (2112), and 256 explicit cases grouped by the class they cover. No difference. The front matter (its title, `config` and `displayMode`) is read with this module, so a front matter that does not parse is an error for every diagram. Shared with M3 from step 7 onward.

Text, done: `crates/ferrigura-text` (fonts, measurement with harfrust, line metrics, Mermaid's wrapping, styled runs, subsetting with per-subset family names) is merged from its own worktree. Verified against Chromium in a fixture (180 widths, 24 boxes, 27 wraps, 7 styled-run lines) and against the spike's Rust binary. Deviations from the spike: the subset family name is a 16-hex-digit FNV-1a hash, not six digits; `wrap_line` takes one face, although Mermaid wraps styled words per word (styled runs are measured per run); no fallback fonts, WOFF2 or caching yet. The spike's generator for the Chromium fixture is not committed.

Known gaps in the configuration: `themeVariables` are not computed (the theme port does that in Stage B), and they are left out of the comparison; non-finite numbers (`.inf`, `.nan`) are carried as the strings `"Infinity"`, `"-Infinity"` and `"NaN"`, because a serde_json value cannot hold them (a theme reads `THEME_COLOR_LIMIT` from there); a `config` key in a directive maps to the section of pie and info only; a directive whose arguments are not an object (a word, a number, an array, a string) contributes nothing, as the reference's merge ignores such values, and 13 explicit cases in `config-cases.ts` show it; the front matter `config` block is ignored when it is not an object, which the same cases check.

## M4 handover

Done, for review: the ELK Layered port (`crates/ferrigura-elk`), bit-exact with elkjs 0.9.3 (ELK pin 9bc93474e) for the layered algorithm on the options Mermaid sets. Verified on `51c211525` (this branch, merged with `main` at `5413c8047`): `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` (1348 tests) pass; the corpus has 165 of 169 cases passing, and all 165 match elkjs in coordinates and in the trace with logs; 1200 of 1200 random flat graphs and 900 of 900 random compound graphs match.

Ported: the five phases of the layered pipeline with the processor order that elkjs logs; DEPTH_FIRST and GREEDY cycle breaking; network simplex layering; the layer sweep with barycenter, the two-sided greedy switch and the model order (including the first-try flag that elkjs shares between its two tries); Brandes & Koepf placement; orthogonal edge routing; node, edge, centre and end labels, with their sizes and placements, and the LEFT and UP mirror of node labels; self loops with one edge; layer constraints FIRST and LAST; the separate handling of connected components; nested graphs laid out level by level; compound layouts (`INCLUDE_CHILDREN`) with cross-hierarchy edges, hierarchical ports on the east and west sides, and inverted ports; explicit ports on east, west, north and south sides, with one edge each; the random source and the GWT merge sort. The Java semantics that elkjs has and the source does not show are written down where they occur, with the probe or log that settled them.

Unsupported, and why:

- Hyperedges (a port with several edges, `synthetic__explicit-port-shared`): Mermaid never creates an ELK port (its edges name nodes), so it does not reach them.
- Compound gaps that the 900 random compound graphs do not reach, each raising its own message: north and south external port dummies and a fixed order of east and west external ports (both need fixed-side or fixed-order ports on compound nodes, which Mermaid does not set); in-layer constraints (they come only from north and south external ports); inside self-loops (`elk.insideSelfLoops.activate`, commented out in Mermaid's option catalogue); allowing non-flow ports to switch sides (needs port constraints); north and south self-loops at north and south ports (needs explicit ports on those sides).
- Splines and polylines (`edgeRouting` other than orthogonal, self loops with a polyline or spline router): outside the option inventory.
- The one-sided greedy switch (`GreedySwitchType.ONE_SIDED`): no default or corpus case reaches it.
- Non-layered algorithms (`elk.box`, `elk.rectpacking`): the port runs `elk.layered` only; they are the three cases named in `NOT_PORTED`.
- Port labels, an explicit port anchor, and a port without a side: refused with their names.

How to run the random sets (from the repository root):

- Flat: `pnpm exec tsx crates/ferrigura-elk/tools/random-graphs.ts --count 1200`, then `cargo test -p ferrigura-elk --test random_graphs -- --ignored --show-output`.
- Compound: `pnpm exec tsx crates/ferrigura-elk/tools/random-compound-graphs.ts --count 900`, then `cargo test -p ferrigura-elk --test random_compound_graphs -- --ignored --show-output`.
- The graphs are written under `target/` (not tracked). Each tool takes `--seed` and `--out`; the tests read `FERRIGURA_RANDOM_GRAPHS` or `FERRIGURA_COMPOUND_GRAPHS` when set.
- The corpus: `cargo test -p ferrigura-elk --test differential -- --nocapture` and `--test trace -- --nocapture`. Synthetic cases are regenerated through Node elkjs with `pnpm exec tsx crates/ferrigura-elk/tools/capture-corpus.ts --synthetic-only`; the full capture also drives the browser and was not run for this handover.

Known gaps and notes: no indexed hash collection is iterated by a processor yet, so `indexmap` with `shift_remove` is not needed; the six intermediate commits of the inverted-port series fail the compound random test on their own, and only the tip is green in that run; the commit trailers of this branch name Claude Haiku 5.5. The branch is local and not pushed. It is ready for review and for the merge into `main`, which the user decides.

- **Parsers**: `crates/ferrigura-syntax/src/<type>/`, hand-written for the Jison and Langium grammars alike (decision 0002), each with its DB rules and its canonical model in `ferrigura-model`. The YAML front matter is a state-by-state port of js-yaml 4's loader (`yaml.rs`); detection follows the reference's order, front matter after blank lines included.
- **Layout engines**: `ferrigura-cose` holds cose-bilkent 4.1.0 (mindmaps, on cose-base 1.0.3 and layout-base 1.0.2) and fcose 2.2.0 (architecture, on cose-base 2.2.0 and layout-base 2.0.1, with the spectral start and the two runs Mermaid makes, drawn from the mulberry32 of `architectureSeed.ts`); `unified/tidy_tree.rs` is Mermaid's removed tidy-tree package (`layout: tidy-tree`), vendored as its reference under `tools/port/vendor/`. Each is exact on its captured corpus.
- **Browser arithmetic**: `ferrigura-jsmath` gives Chromium's `Math` functions bit for bit (correctly rounded `sin`, `cos`, `tan`, `asin`, `acos` and `log`; `atan` and `atan2` from llvm-libc; `pow` and `hypot` from V8), and `ferrigura-path` gives Chromium's `getBBox()` of an SVG path (Blink's parser and builder, Skia's conic arcs and tight bounds in float), which sizes the mindmap's cloud and bang nodes, where the force layout amplifies a one-unit difference into tens of pixels.
- **Renderers**: requirement and mindmap on the unified renderer (new shapes: the requirement box, the block composite and arrow, the mindmap circle, cloud and bang); block on the unified shapes with its own layout; the others in their own folders on `common/`, whose d3 part grew by the ordinal scale, the d3-array reductions, V8's `Array.prototype.sort` (TimSort, since NaN comparators make the order depend on the algorithm), d3-hierarchy's treemap, d3-format, and d3-sankey's layout (in `sankey/`).
- **Sanitising**: `sanitize.rs` runs DOMPurify twice on the strict path, as the reference does, with Mermaid's anchor hooks (`rel="noopener"` for `target="_blank"`, in the reference's attribute order).

Verified before the merge:

- `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace --no-fail-fast` (4622 passed, 102 ignored) pass; prettier and eslint pass on `tools/port`.
- Parsers: every P2 type without a difference or a named exception (inputs in the table below), with the layout data of requirement (266 inputs) and kanban (355); the configuration (6452 inputs, every type in its own scope), YAML (4447 inputs) and the theme (110).

The P1 types and flowchart are unchanged (flowchart 298 of 298 with the ELK input equal in all 298).
- CI runs every differential above and the geometry of every M6 and P2 type.

How the harness changed in P2: the page maps the fonts the reference names itself (`trebuchet ms`, `verdana`, `arial`, `Helvetica Neue`, `Helvetica`, `Open Sans`) onto the bundled face, and its viewport and screen are 1200 by 900 px with no body margin; a type may have probe inputs under `tools/port/geometry/probes/<type>`; the eventmodeling box text is compared line by line like the journey's labels, with its code pinned to the bundled mono face; the same non-finite number on both sides agrees; a fixture is excluded for uncovered symbols only when they are in the text a diagram draws (the body and the front matter's `title`); the reference page installs no-op capture hooks for cose-bilkent, fcose and the tidy tree, whose corpora their capture tools write.

Known gaps:

- eventmodeling: `sub`, `sup`, `small`, `big`, `kbd`, `p` and `div` in data are drawn as plain runs, where the reference changes the line, the size or the face (`eventmodeling/PLAN.md` 8.4).
- treemap: the label truncation counts characters, the reference UTF-16 units, so an astral character may be cut differently (not probed).
- mindmap: `layout: elk` lays the mindmap out with ELK, where the reference crashes for every mindmap (a named exception); `swimlane` falls back to cose-bilkent; the classic themes' default node is not ported (redux themes only, as M6 decided).
- architecture: the unknown icon's question mark keeps the reference's `ArialMT, Arial`, which ferrigura does not ship; the fcose corpus was captured on a page that measured labels in the system's Helvetica Neue, so 19 of its run-1 bounds differ by half a pixel from the harness's mapped face (the engine tests replay the captured input and are unaffected; a recapture through the harness page would align them).
- ferrigura-path: 81 of the 3011 generated corpus paths differ from Chromium, all within 0.05 px but one (0.094 px on a path 293,000 px across), because Chromium takes the macOS libm's float `sin`, `cos`, `tan` and `atan2`, which are not correctly rounded for a few inputs; the port takes the correctly rounded values, the same on every host. Mermaid's cloud and bang paths are not among them.
- block: an edge path's `data-id` is the doubled id where the reference writes the prefixed one, and `data-points` is not written (neither is in the geometry key).
- sankey: the dark custom properties are written but not compared (the harness forces redux-color); the schema says `useMaxWidth: false` where the built default is true, which the port follows.
- Code to share: `Math.max` exists in more than one module (`common/d3/math.rs`, `unified/tidy_tree.rs`, `unified/shapes/polygon.rs`), and eventmodeling borrows journey's text helpers, which belong in `common/`.
- As in M6: `htmlLabels: true` is drawn as SVG text (decision 0004), fallback fonts for uncovered scripts, images and icon packs.
